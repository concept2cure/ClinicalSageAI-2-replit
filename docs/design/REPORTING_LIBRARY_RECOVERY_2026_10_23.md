## Completion contract

1. Confirm schedule creation only from the expected successful HTTP response and a coherent returned row matching the requested report/scope/explicit recurrence and delivery fields. Confirm enablement only for the requested positive safe-integer ID and requested state. Confirm bundle creation only from a coherent canonical bundle ID, name and exact selected run set. Missing, conflicting or mismatched positive receipts are unconfirmed; they never announce success or clear input/selections.
2. Reuse the existing API normalizer, code decoder and mutation classifier. Transport failures, generic server errors and contradictory receipts use neutral recovery copy: the write may have completed. Never claim a lost response proves no request reached the server. Preserve precise authorization/configuration/CAS refusals and the pre-write bundle size refusal.
3. Backend bundle absence is stated only when the transaction failed before COMMIT and rollback was acknowledged, or an explicit pre-write check refused. A COMMIT acknowledgement failure, rollback failure or post-COMMIT cleanup error yields `REPORT_BUNDLE_OUTCOME_UNKNOWN`, a safe check-current-bundles message and no retry claim. Suspect connections are discarded. Other existing helper callers retain their error identity and authorization behavior.
4. Bundle errors add explicit `recordingOutcome: 'not-recorded' | 'unconfirmed'` and `retryAllowed` metadata. The client trusts the known 503 rollback only with a coherent negative envelope, `REPORT_BUNDLE_NOT_RECORDED`, `recordingOutcome: 'not-recorded'`, `retryAllowed: true` and no positive receipt. Old 503 codes without that proof remain uncertain. Unknown outcomes carry `retryAllowed: false`. Size 413 remains a precise pre-write refusal.
5. Synchronous in-flight guards cover create and per-row enablement dispatch. Pending controls show existing busy styling/text. No automatic mutation retry occurs.
6. Pending/unconfirmed knowledge belongs to the existing canvas account owner and survives library tab changes. A lost response keeps the attempted draft/selection and blocks blind repeat. A confirmed completion received after a tab unmount is retained until the current same-context panel consumes it once; a restored completed draft must not become a writable duplicate. Check schedules/bundles performs a read; a read alone, an absent row or a bounded list never proves the earlier write did not occur. A further write requires deliberate review/new-request intent, with clear copy about that limit. Failed/malformed refreshes, contradictory success/error envelopes, missing-store notices and duplicate/conflicting row identities do not clear the hold.
7. Use the existing account/context owner before dispatch and after asynchronous stages. Late old-context completions do not announce success, clear new selections or adopt old form state. Minimal pending/uncertainty metadata can settle for its original owner; it must not expose old project content in the replacement context. Ordinary bearer refresh remains supported. No second session mechanism is added.
8. Retain the existing layout, controls, classes, entitlement/current-role checks, export behavior and explicit signature ceremony. Recovery controls use existing notice and button furniture.
