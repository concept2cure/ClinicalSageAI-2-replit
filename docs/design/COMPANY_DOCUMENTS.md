# Company identity, letterhead and legal documents

This user-authorized extension supports D2 onboarding and D7 submission preparation within Admin, Authoring, Submission Center and Reporting. Evidence is recorded under `docs/evidence/COMPANY-DOCUMENTS/`. It does not assert that a company document satisfies every agency's legal requirements.

One organization profile lives in `organizations.settings.companyDocuments`, through the existing atomic tenant settings writer. It stores identity, the canonical TemplateSpec, presentation defaults, a revision and a registry of immutable Vault version pointers. No legal file bytes live in settings. Admins/owners manage the profile; authenticated organization members read permitted assets. Reads and writes retain tenant and project access checks. Mutation reasons and optimistic revisions prevent silent overwrites.

`GET /api/client-branding/company-documents` returns `{data: CompanyDocumentProfile, canManage}`. `PUT` accepts `{expectedRevision, reason, companyName, address, contact, registrationDetails, letterhead, importedFrom, applyToReports, applyToSubmissionCorrespondence}`. Legal entries are registered separately by `POST /company-documents/legal-documents` with `{expectedRevision,reason,title,kind,programId,vaultDocumentId,agencies,countries,submissionTypes,language,effectiveOn,expiresOn}`; IDs, version, hash, registration identity and current Vault approval are server-derived. `DELETE /company-documents/legal-documents/:id` archives metadata, retaining source bytes. It accepts `{expectedRevision,reason}`. Mutations return the same profile response.

The designer imports existing Word/PDF formatting via `/api/c2c/templates/extract`, edits the same TemplateSpec used by existing generators, accepts validated raster logos, and previews the resulting page. Plain text fields are escaped. Existing agency forms and signed legal documents are never decorated or rewritten. A styled correspondence download uses the existing DOCX renderer, not a second generation engine.

The same component is reachable in Admin → Settings and organization Setup; Reporting links to Setup. The designer covers company identity, logo, page size/orientation/margins, typography, accent, running header/footer, confidentiality and page numbers. The preview is illustrative; the saved Word download verifies final pagination. Imports extract editable formatting, not an exact facsimile of arbitrary stationery. Both automatic presentation preferences default off. `POST /company-documents/letterhead/render` accepts optional `title`, `paragraphs` and `purpose: company | submission`. Manual company downloads always use the saved design. Submission Builder's correspondence action passes `submission` and uses a neutral template when its preference is disabled. Downloads are audited drafts; users review their content and explicitly ingest/place a reviewed PDF before filing.

Legal library entries identify exact Vault versions and their effective/expiry dates, language, agency, country/region and submission type. Empty applicability lists mean unrestricted applicability, not proof of agency acceptance. Nonmatching, expired, superseded, unapproved, missing, inaccessible or changed versions cannot be included. Submission attachment is explicit, with a filing section and reason, through the existing Vault leaf placement. Cross-program reuse is an explicit copy into the target program through canonical Vault ingest; the copy requires its own review. Source signatures are retained in the unchanged bytes; approvals are never transferred by the UI.

`POST /company-documents/legal-documents/:id/place` accepts only `{sequenceId,sectionCode,reason}`. The server derives the admitted submission's program, agency, region and application type, then calls canonical Vault leaf placement. `POST /company-documents/legal-documents/:id/copy-to-program` accepts `{programId,expectedRevision,reason}` and requires a company administrator plus current source access and target Vault write permission. It verifies the original PDF hash, copies exactly those bytes, rechecks source access/approval at ingest commit, audits source provenance and registers an independent draft. A copy that commits but cannot be registered returns an explicit partial-success message; it never claims rollback or approval. The normal Vault transmission gate also checks active registered versions' dates and hashes, so expiry after placement prevents transmission. Archiving retires a library entry, not the underlying Vault document or its independent approval.

Applicability is also enforced in canonical `upsertLeaf`, covering ordinary Vault, REST and AnA placements. This gate permits draft placement for review while enforcing active registered legal scopes and dates. Packaging, dispatch readiness and source-evidence checks pass the actual tenant-bound sequence/submission context to the existing Vault transmission gate; the requested output region is never treated as the filing's authority. Registered restricted documents fail closed when that target cannot be established, while unregistered ordinary Vault files keep their existing behavior. Transmission still requires current approval for the exact bytes, independently of placement.

Reports may use company presentation defaults without changing their sealed underlying content or obscuring draft/validation/signature labels. The export audit records the branding revision and profile hash. Users can download legal originals from the library to accompany reports separately; branding does not automatically attach them to report packs. Unknown agency/country scope refuses submission placement instead of assuming a global legal obligation. Scope labels match the existing canonical filing agency, region and application-type identifiers case-insensitively. Language is recorded for review, rather than used to infer an agency's translation requirements.

All settings writes retain the managed company section unless they use its dedicated validated writer. Generic organization, tenant-config and AnA settings reads omit the private registry rather than bypassing its project ACL. Atomic settings audit details record revisions, hashes and changed immutable legal references, without copying company prose, logos or legal file text into audit rows. No new schema migration, production dependency or alternative storage pipeline is introduced.

Date-only validity uses UTC calendar days, including the expiry date itself. The settings-backed registry retains at most 500 entries including archives; archiving does not erase history or free that capacity. Replacement legal metadata is registered against a current immutable version after archiving the old entry. The company library is an inventory and reuse mechanism, not a substitute for current jurisdiction-specific legal review.

Shared contract: `shared/company-documents.ts`; canonical rendering contract: `shared/templates/template-spec.ts` (re-exported from the existing server path). Required verification covers authorization and tenant/project isolation, concurrent edits, upload safety, original byte/hash retention, expired/mismatched/legal approval refusals, designer persistence and preview, reachable Admin/Settings and submission selection, and actual branded export content. No new production dependency is required.
