# Submission Center required deliverables — UI implementation design

W1 / D2, concept2cure-v2, 2026-10-14. Root authorized this bounded UI implementation after reviewing [the continuity assessment](REGULATED_WORKFLOW_UI_CONTINUITY.md). This design was filed before UI source changes. The [reviewed backend contract](SUBMISSION_REQUIRED_DELIVERABLES.md) and shared/types/submission-api.ts now provide the exact shared ABI, server-confirmed compatible frameworks and admitted optional program/source labels. Actual client red/green results are filed separately in this phase evidence. Root owns runner slots, compiler, native request/source proofs, browser and publication gates.

## Intended client behavior

Add **Required deliverables** to the existing Submission Center workspace tabs. The existing submission selector and one SeqPicker continue to choose the real retained submission and sequence. A focused sibling renderer displays the supported framework's structural/content coverage, real source references and unresolved questions. Existing Builder, Validation, Shadow review and Dispatch retain their governed behavior.

The heading names the evaluated framework and working sequence, followed by the actual recorded submission/program identity returned by the server. A scope notice says: **Coverage of retained material placed in this sequence. This view does not approve the documents or clear the submission for dispatch.** Show authoritative scope inputs and whether the evaluation used a recorded or explicitly compatible framework. Do not turn a server ready boolean into Approved, Filing ready, full CTD complete, a progress percentage or a new dispatch control.

No new global app, WBS store, editor, copied taxonomy, theme, icons or dependencies. Use pj-card/pj-card-h/pj-card-b, cm-pushbar/sc-seqbar/sc-field/sc-subpick, existing ub-inv tables, rd-chip tones, scaf-note, EmptyState and the existing notice/error rendering. The sc-wsbar and sequence controls already wrap. Place the table inside the existing cm-matrix scroll wrapper; keep source prose wrap-safe and do not hide unknown/pin states on mobile. Review desktop/mobile and light/dark after the actual implementation and gates are green.

## Framework support and unavailable states

Current server PATHWAYS has ten non-eCTD engines: ctis, mdr, ivdr, estar_510k, estar_de_novo, pmda_shonin, pma, prestar_q_sub, prestar_ide and prestar_513g. The inspected baseline shared Pathway named only six; the backend owner reconciled it to the canonical ten-value SUBMISSION_DELIVERABLE_PATHWAYS constant and derived Pathway type. This UI uses that one shared runtime vocabulary. No client import from server and no second client list pretending to define compatibility.

IND, NDA and BLA have canonical requirements/catalogue and eCTD validation code, but do not have this universal pathway-manifest engine. Required modules/forms in /requirements are a reference backbone; a manually supplied name or template-id set is not sequence coverage. For these filings show an honest notice, such as **A sequence coverage catalogue for this filing type is not available in this view. Open Validation for the existing governed assessment.** Do not call the non-eCTD route with an invented IND/CTD pathway, map a drug filing to a device framework, or render unsupported coverage as zero missing. BLA versus IND is established from recorded facts, never title/product or sequence.type.

Framework choices must come from reviewed shared constants/catalogue with recorded compatibility, or from a server-confirmed supported selection response. The backend proposal permits explicit compatible query selection and rejects mismatches. The UI must not infer a recorded filing from a selector value. No automatic framework default until authoritative recorded facts establish it. CTIS member-state inputs are explicit validated state codes; don't derive states or not-applicable declarations from source titles, flags absent from metadata, or primaryRegion. The reviewed response carries exact validated/de-duplicated/canonically ordered memberStates and regulation: mdr|ivdr|null. The manifest read uses programId and submissionId as expected selected identities. It omits pathway only for a positively recorded compatible default (inputOrigin recorded), and sends pathway for an explicit compatible choice (inputOrigin explicit-compatible). MDR/IVDR manifest scope carries its matching regulation; other frameworks carry null. CTIS_MEMBER_STATE_CODES is the shared ISO 27-code vocabulary, including GR. Normalize explicit input by uppercase, de-duplication and sorting; never rewrite GR to EL. Empty state inputs remain unanswered, and invalid codes show an input warning without an invented evaluation. Missing subtype/applicability facts remain canonical backend unknown/refusal outcomes.

## Proposed status rendering

| Backend fact | Existing-style display | Meaning retained |
| --- | --- | --- |
| present | Present chip, actual retained sources | Only the positive structural/content evidence established by the backend; never approval. |
| missing | Missing chip | The evaluated required slot lacks admitted substantive retained material. |
| optional-absent | Optional; no material placed | Does not mean an unknown condition was answered or waived. |
| undetermined | Undetermined chip + safe reason/needed fact | Unanswered applicability, unreadable/unverified content or source proof; never demoted to optional-absent. |
| not-applicable | Not applicable chip + recorded/evaluated explanation when supplied | A known explicit applicability result; no client toggle to waive a requirement. |
| source pin mismatch | Source content changed chip beside that exact source | Separate evidence axis; preserve backend slot status and reasons rather than overwriting the row status locally. |
| source unpinned/unverifiable | No content pin / Pin could not be verified | Never a source verified or present assertion fabricated from a pointer. |
| source content non-substantive/undetermined | No substantive retained content / Content could not be determined | Distinct from missing row, absent store, changed pin and draft lifecycle. |
| source lifecycle draft/unverified/finalized | Draft / Lifecycle unverified / Retained finalized source, using reviewed contract copy | Lifecycle is independent of structural coverage and the pin; finalized is not dispatch clearance. |

Group rows by the server's ordered group/path; preserve exact status/required flag and current source evidence. Suggested columns: Deliverable, Requirement, Coverage, Retained source. Required, optional and unknown applicability need their own truthful text. Totals are the backend's actual section, required-present, required-missing and undetermined counts; do not synthesize a success percentage or claim completeness when applicability is unresolved. A source's pin/lifecycle/content badges stay beside its own identity. Optional programCode/programTitle and sourceRef.label are shown only from the admitted server response, with identifiers retained as smaller trace references. Missing legacy labels are accepted; invalid present label types are refused. Labels never participate in identity matching. Multiple matched leaves with the same code or title remain distinct by actual leaf id; no reverse lookup of a sources label string.

Read states remain distinct: no selected submission, unreadable submission list, no sequence, sequence read failure, select compatible framework, unanchored/conflicting scope refusal, unsupported catalogue, loading, malformed/incompatible success response, access refusal, unavailable source evaluation, evaluated missing/undetermined material, and a genuinely valid zero-entry evaluation. Empty entries without authoritative catalogue/scope/evaluation semantics are a failed read, not 'nothing is required'. Retry uses the same current selection and owns a new request generation; do not show the last success underneath a new error or scope.

## Request/result continuity design

The new renderer owns one local scoped read state, request generation and alive ref. It uses canonical apiRequest and error/message redaction; no new fetch convention. At render, state is visible only if its loaded context key equals the **current** key and its captured sameRevision guard still passes. This check precedes effects, so obsolete rows or source controls cannot paint under a newly selected program/account. The scope key includes actual actor/org, reactive open shell program, organization/project list mode, actual selected recorded program, submission id, sequence id, evaluated framework and normalized member-state/applicability inputs, plus relevant sequence revision/status if the reviewed response uses it. These values are identities, not display names.

Before apiRequest: increment generation, clear previous payload/error, capture session guard and exact requested context. After apiRequest, after JSON/error-body parsing, and in catch: require alive, latest generation, same context and sameRevision. An old success, old error, old retry/finally handler and delayed body result publish nothing; no toast is necessary for this read pane. Cleanup invalidates generation. Automatic token refresh within a still-valid session revision may finish. Session logout/expiration/adoption/account replacement invalidates visible data and all source actions; subscriptions to existing auth events may trigger the local re-render but must not create a new auth store or mutate authService.

Validate the reviewed response before publication: authoritative organization/program/submission/sequence must equal selected/requested identities; actual evaluated framework, normalized member states and regulation/subtype inputs must match the requested evaluation; entries/totals/status/source refs must have the expected runtime shapes. A 200 mismatch is unavailable, not an empty view. Backend expectedProgramId/expectedSubmissionId guards remain server-owned; client equality checks add continuity, not authorization.

The inspected parent retained old submission/sequence arrays on the first render after path change; the controlled red reproduced that committed picker mismatch. Root-approved strict view identity does not by itself establish current provenance of those selector reads. **Implementation must gate request initiation on a current, settled selection read**, not loading:false from retained old state. The approved implementation replaces only those two existing read call sites using submissionScopedRead.ts. The hook returns loadedScope, masks obsolete rows synchronously and captures the canonical session guard after every awaited transport/body/error path. It retains one canonical GET each, existing row-envelope behavior, refetch bumps and four-state outputs. The sibling issues only the current manifest read. Global dataConnect and authService remain untouched. The backend owner separately adopted ordinary public selector/Builder reads to the current request access boundary.

Changing workspace should preserve the established selected submission/sequence. Returning to Required deliverables performs a current read rather than resurrecting an old result. Changing program, submission, sequence, framework, member states or session immediately hides obsolete results and source actions. Input selections belong to one submission/program/session; clear framework/member-state choices when that identity changes. Do not silently carry DE into another filing or substitute a near-matching sequence. Preserve the user's selected sequence across adjacent workspace navigation and an ordinary refresh only when the same current row still exists.

## Exact retained-source editor handoff

The reviewed shared sourceRefs/editor envelope carries actual admitted retained identities. Only a positively verified editor.kind=authoring-document with an actual authoring_documents UUID and current verified source program may show Open saved document. Pass setEditorTarget({docType:null,docId:<actual id>,programId:<actual program>,...(verified source sectionCode ? {code:...} : {})}), then existing onNav('document-authoring'). Recheck current result/generation/session/scope at the click. Never pass the leaf filing sectionCode as a source section, a sources display label, title-based match, numeric legacy key or Vault UUID as authoring docId.

The target program must agree with the active shell program before editor navigation. A user deliberately listing another program's submission may inspect an admitted server result; source actions in this view must disclose that another program is selected and remain disabled until that program is explicitly opened through the existing project flow. Do not silently publish a different shell program. All unsupported/unverified stores remain an exact disclosed read-only reference without an editor link. For a verified multi-section retained copy, open the actual saved document; do not invent a section target. No 'opened' success toast before the editor has resolved the target.

Existing editor unsaved-work protection remains the authority. The new view holds no editable document. Integration tests must prove exact document targets still pass through DocumentWorkbench's requestLeave when typed unsaved work appears during target resolution, and cancel/save-and-leave/stay outcomes remain unchanged. No editorTarget or editor source changes are proposed; if that existing behavior needs alteration, return it as a separate root-owned boundary rather than widening this slice.

## File ownership and verification sequence

The approved UI ownership is new SubmissionRequiredDeliverables.tsx, minimal SubmissionCenter.tsx wiring, one shared/types/submission-ui.ts workspace entry, focused UI tests and this phase evidence. The exact response types remain backend-owned in shared/types/submission-api.ts. submissionScopedRead.ts contains the approved local selector/read lifecycle logic, keeping the new helpers below complexity/size budgets and avoiding new warning occurrences in the parent. New sibling owns display, runtime response check, read lifecycle and exact-source click checks. Parent wiring owns the existing tab/selection gate and reactive shell context. Shared contract/workspace metadata was coordinated with the backend owner/root. The only additional approved SubmissionSeqWorkspaces change admits the canonical undetermined source-resolution status and displays Source evidence undetermined as a warning chip, preserving actual missing/content-changed verdicts and existing governed actions.

The preparation matrix at /tmp/submission-deliverables-ui-prep/stale-result-test-matrix.md defines prospective meaningful tests. First show controlled red from the unchanged UI/response adoption behavior after ABI approval and root runner-slot grant, then implement the bounded change, run new plus impacted existing tests and scoped lint once. Record source pins, actual red/green counts, exact logs and limitations in a new phase folder; never rewrite prior reporting evidence. Native actual request/source/privacy proofs remain backend-owned. Browser review must use persisted fixtures with verified current identities, not mocked readiness. No production readiness, full CTD infrastructure or dispatch authorization claim follows from this bounded client increment.

Backend ordinary public selector/Builder read call-site adoption is now separately assigned to the backend owner. The UI still treats access as a fresh server decision and this phase does not qualify adjacent writers or the entire Submission Center by inference. Existing technical-file assemble/export writers also retain their independent qualification boundaries. This UI must not conceal those limits behind a green structural count.

## Confirmed verdict preservation addendum

The first integrated client replay passed 248 of 249 cases across 23 suites. The unchanged lifecycle QA caught one real regression: synchronous same-sequence refresh masking unmounted Builder before its local server-confirmed leaf-removal/revalidation notice survived. That actual failure is retained separately. The approved bounded fix passes the existing Notice through Builder's existing onSequenceChanged callback when its existing write effect requests a sequence refresh, publishing it in the existing parent VerdictNote before refetch. Ordinary Builder notices remain local. Success still describes only the server-confirmed result; an existing uncertain-outcome refresh remains an uncertainty, not an optimistic state transition.

A parent selection generation changes on current program/submission/session/selected-sequence context, including away-and-back navigation. The promotion requires that exact generation, current sequence object, current scoped-read request generation and sameRevision. Scoped promoted notices are hidden immediately after ownership changes and do not appear under another sequence. During a same-record refresh the confirmed notice remains visible independently of the unmounted pane. Two additional actual delayed-write controls cover sequence-away-and-back and replacement account. The focused four-suite preservation replay passed all 80 cases with zero skips and no new-suite act warnings; final integrated replay and source/artifact pins are recorded in the phase evidence. No write policy, lifecycle transition, new store or governed action changed.
