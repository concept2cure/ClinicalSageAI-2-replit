## 1. Method

As OQ-001 §1. Since v0.5 the review is requested on a review route naming a second identity, `OQ_SIGNER` (`OQ_SIGNER_EMAIL`, `OQ_SIGNER_PASSWORD`, `OQ_SIGNER_TOTP_SECRET`; `tests/validation/lib/credentials.mjs`), and the review signature steps (OQ-AUTH-12, 13, 14) are that reviewer's: the ceremony re-authenticates them with their own password and, when they have an authenticator enrolled, a current code the harness computes and never reuses (`tests/validation/lib/totp.mjs`). The freeze (OQ-AUTH-11), OQ-AUTH-13 (c) and OQ-AUTH-13b re-authenticate, or are refused before re-authenticating, the run identity (`VALIDATION_USER_PASSWORD`, `VALIDATION_USER_TOTP_SECRET`). No password or code appears in any record. Without the second identity the credentialed steps are recorded "not executed — credential not supplied"; without the run identity's password the freeze is a deviation with that reason. Until v0.4 the steps enrolled and used a separate signing PIN, which the product no longer has. Steps execute in the order below: review/submit precede freeze because submit requires DRAFT; the AI-draft steps precede freeze because a FROZEN document refuses every edit-class route; the comment from OQ-AUTH-09 is resolved through the product's comment-resolution API (OQ-AUTH-11b) before the freeze, after the refusal of a freeze over an open comment has been observed (OQ-AUTH-11a). The freeze confirm flag `acknowledgeUnresolved` is never sent.

## 2. Pre-conditions

IQ-001 executed; a program created by OQ-AUTH-00. Since v0.5, a second identity (`OQ_SIGNER_*`) in the run identity's organisation that holds signing authority (role admin, approver or reviewer), is not the run identity, can open the program's project, and has an authenticator enrolled through the product's own enrolment endpoints. The AI-provider steps expect `ANTHROPIC_API_KEY`/`OPENAI_API_KEY` to be **unset** for the fail-closed check and set to a PQ-passed model for the drafting check.
