# AnA Agentic Onboarding — P2/P3 Build Spec (contract-first)

> Generated by a contract-first mapping team (6 mappers + synthesis) over the real codebase.
> Design decisions fixed: org-profile + first-program + contact fields; propose-all, flag <0.7; NEVER auto-commit (human approves every field); PDF/DOCX/XLSX <=20MB; extract-only.

## Shared proposal contract
```ts
// shared/onboarding-proposals.ts — NET-NEW. THE single source of truth. Imported VERBATIM by
// (1) the server extract service + ingest endpoint, (2) the onboarding_ingest AnA tool handler,
// (3) the ProposalsReview UI. Lives in shared/ so both `server/*` and `client/*` import the SAME
// type (codebase already shares types this way, e.g. `@shared/schema`). This module is where
// wiring bugs are prevented — do not redeclare FieldProposal anywhere else.

/** Closed union of every onboarding field a proposal can target. Drives the P3 backend fan-out,
 *  the AnA tool output, and the review-row rendering — all three key off THIS union. Comments show
 *  the verified persistence target from shared/schema.ts. */
export type OnboardingTargetField =
  // ── Org profile ──────────────────────────────────────────────────────────────
  | 'org.name'            // organizations.name (notNull, governed PATCH) [+ clientIntelligenceProfiles.companyName]
  | 'org.clientType'      // organizations.clientType enum: medtech|biotech|pharma|diagnostics|cro|health
  | 'org.industryArea'    // organizations.industryMode (nullable) | clientIntelligenceProfiles.industry/subIndustry
  | 'org.therapeuticArea' // clientIntelligenceProfiles.therapeuticAreas (json[]) — ONLY tenant-level home (schema L14867)
  | 'org.address'         // clientIntelligenceProfiles.headquarters (single free-text line, L14860). Structured address = DOCUMENTED-NULL / NET-NEW
  // ── First program ────────────────────────────────────────────────────────────
  | 'program.code'        // projects.code (nullable, L5201)
  | 'program.name'        // projects.name (notNull, L5200)
  | 'program.pathway'     // NO first-class column → projects.metadata.submissionType (mirror concept2cure.ts L2100)
  | 'program.indication'  // NO column → projects.metadata.indication (nearest real col: projects.therapeuticArea)
  | 'program.phase'       // NO column → projects.metadata.phase
  | 'program.targetDate'  // projects.targetEndDate (timestamp) | metadata.targetSubmissionDate (concept2cure.ts L2109)
  // ── Primary contact ──────────────────────────────────────────────────────────
  | 'contact.name'        // clientWorkspaces.contactName
  | 'contact.email';      // clientWorkspaces.contactEmail

export interface OnboardingProvenance {
  fileId: string;   // uploaded file id — ONLY 'ready' attachments carry one (useChatUpload ChatAttachment.fileId)
  fileName: string;
  excerpt: string;  // the REAL source span the value came from — never fabricated (honesty rule)
  page?: number;    // page/section locator when the extractor knows it
}

export interface FieldProposal {
  targetField: OnboardingTargetField; // closed-union key — the ONLY thing backend fan-out switches on
  label: string;                      // human row label ("Therapeutic area")
  value: string;                      // model-extracted value. STRING (C2CForm values are Record<string,string>)
  confidence: number;                 // 0..1, model-emitted, tied to this fileId. NEVER invented
  provenance: OnboardingProvenance;   // required; a proposal with no real provenance MUST be dropped, not shown
  accepted?: boolean;                 // UI review state — human toggled accept
  editedValue?: string;               // UI review state — human override of `value`
}

/** Design-fixed confidence policy: propose ALL, visibly flag <0.7 as "needs review". Never auto-commit. */
export const NEEDS_REVIEW_THRESHOLD = 0.7;
export const needsReview = (p: FieldProposal): boolean => p.confidence < NEEDS_REVIEW_THRESHOLD;

/** P2 extract envelope — returned IDENTICALLY by the onboarding_ingest tool and POST /api/onboarding/ingest. */
export interface OnboardingIngestResult {
  source: 'AnA Onboarding';
  fileId: string;
  proposals: FieldProposal[];
}

/** One human-approved field, sent to the P3 governed commit. value = editedValue ?? value at approval time. */
export interface OnboardingCommitField {
  targetField: OnboardingTargetField;
  value: string;
  confidence: number;
  provenance: OnboardingProvenance;
}

/** P3 commit request. Carried as `params` of the /api/ana-ri/governed-action sign-off (command:'onboarding.commit').
 *  reason satisfies the STRICTEST downstream gate (>=10 chars) so it passes org-PATCH(min3)/viewReason(min8)/esign(min10). */
export interface OnboardingCommitRequest {
  fields: OnboardingCommitField[]; // ACCEPTED subset only
  reason: string;                  // reason-for-change, >=10 chars
  workspaceId?: number;            // resolved clientWorkspaceId (projects.clientWorkspaceId is notNull — must resolve first)
}
```

## Backend endpoints

### chat upload (REUSE) — `POST /api/chat/upload` (governed=False, audited=False)
- Existing upload→OCR→project-memory path. P2 uses it only to obtain a fileId; extraction into proposals is a separate step. VERIFIED: useChatUpload posts here and returns {fileId, extractionMethod, extractionWords}.
- request: multipart {file, projectId?} + Authorization Bearer (getAuthHeaders(); cookies alone 401)
- response: { fileId, extractionMethod, extractionWords }
- mounts: existing mount (already wired for Composer/AnaRail/AnaDock)

### onboarding ingest (NET-NEW, P2) — `POST /api/onboarding/ingest` (governed=False, audited=False)
- Deterministic backbone for P2: fileId → FieldProposal[]. Reads the file's already-extracted text and calls the NET-NEW extractOnboardingProposals service. Read-only, no writes. Preferred over relying on the model to pick the tool (selectToolsForTurn may trim a brand-new tool).
- request: { fileId: string } + Bearer
- response: OnboardingIngestResult (shared/onboarding-proposals.ts) = { source:'AnA Onboarding', fileId, proposals: FieldProposal[] }
- mounts: NET-NEW router mounted behind authMiddleware (mirror register-inline-routes.ts:768 app.use(path, authMiddleware, router))

### governed-action sign-off (REUSE, P3 transport) — `POST /api/ana-ri/governed-action` (governed=True, audited=True)
- Existing Part-11 sign-off transport. GovernedActionSignoff/useGovernedAction post here. P3 reuses it AS-IS to carry the human approval — no new UI endpoint. VERIFIED SubmitSignoffArgs = { command, params, reasonForChange, password?, mfaToken? }; returns CommandResult under `data`.
- request: { command:'onboarding.commit', params: OnboardingCommitRequest, reasonForChange: string, password?, mfaToken? } + Bearer
- response: { data: { success:boolean, message:string } }
- mounts: existing /api/ana-ri mount (Bearer-only authenticateToken)

### onboarding.commit governed command (NET-NEW, P3) — `POST (ana-ri command, runs behind /api/ana-ri/governed-action) command name: onboarding.commit` (governed=True, audited=True)
- THE governed commit. Human-triggered only. For each approved field: resolve/create default workspace if needed, capture before-image (db.select), write to the mapped table (org→governed organizations update; therapeuticArea/address→clientIntelligenceProfiles upsert; program→projects insert mirroring concept2cure.ts L2089; contact→clientWorkspaces), capture after-image (.returning()), then AWAIT auditService.logAction stamped with agentAuditDetails. Runs in the ana-ri CommandContext so it has userId/organizationId/threadId/chatMessageId + validated reason via requireGovernedToolGate.
- request: OnboardingCommitRequest { fields: OnboardingCommitField[], reason, workspaceId? }
- response: CommandResult { success, message, committed?: {targetField, resourceId}[] }
- mounts: NET-NEW governed command registered in the ana-ri command system (mirror mdx-command-handlers.ts qSubCreate L110-122 / sectionApprove L281-293); gated by requireGovernedToolGate (mdx-tool-policy.ts)

### org profile PATCH (REUSE — pattern + fallback target) — `PATCH /api/organizations/:id/profile` (governed=True, audited=True)
- The ONLY existing governed-write reference (validateOrgOwnership + requireOrgAdmin + reason + before/after + auditService.logAction). onboarding.commit MIRRORS this pattern for org.* fields, or the commit may delegate to it directly for name/clientType/industryMode. VERIFIED L251-328.
- request: { name?, clientType?, industryMode?, reason:string(min3) } — at least one field required (refine)
- response: { success:true, organization: updated }
- mounts: register-tenant-routes.ts → /api/organizations (organizations-routes.ts applies router.use(authMiddleware))

## Honesty / Part 11 guardrails

- Confidence and provenance MUST be real model output tied to the uploaded fileId — never invented. A FieldProposal with no real provenance excerpt is dropped, not shown. The codebase is explicit that onboarding UX must not present fabricated data (onboardingWelcome.ts header; P1 deliberately does no data entry).
- NEVER auto-commit. Human reviews and approves EVERY field. The commit is human-initiated via GovernedActionSignoff → /api/ana-ri/governed-action, not a model tool-call. onboarding_commit is an ana-ri command reached through the sign-off, not an autonomously model-callable AnaToolExecutor handler.
- Do not fabricate an audit id / hash / outcome. The audit row is written server-side by auditService.logAction's chained INSERT; the UI outcome is the server's (RailSignoffs / useGovernedAction never invent it).
- 'AnA on behalf of <user>' is not a stored string — it is the (userId = human) + (details.actorKind='agent:ana') pair. Any verbatim rendered phrase is render-time only (NET-NEW).
- Reason-for-change is required and must be genuine, >=10 chars (satisfies org-PATCH min3 / viewReason min8 / e-sign min10). Do not auto-fill or fabricate the reason — it is the human's attestation.
- Extract-only this phase. No regulatory validation of extracted values — surface them for human confirmation, do not assert correctness.
- Do not claim XLSX ingestion or a 20MB cap works: the existing shared upload path (CHAT_UPLOAD_ACCEPT) EXCLUDES .xlsx and caps at 25MB. XLSX extraction + 20MB enforcement are NET-NEW and unverified until built.
- Do not claim a proposals/extract API already exists: /api/chat/upload only extracts text into project memory. fileId → FieldProposal[] and ProposalsReview are NET-NEW.
- Org-profile field commits are admin-gated (requireOrgAdmin). If the approving human is not an org admin, org.* fields cannot be written — say so rather than silently dropping them.

## Risks / gotchas

- ⚠️ XLSX gap: CHAT_UPLOAD_ACCEPT = '.pdf,.png,.jpg,.jpeg,.gif,.webp,.txt,.docx,.doc' has NO .xlsx/.xls, and the extraction pipeline may not parse spreadsheets. The fixed design requires XLSX — net-new accept-list + extractor work before XLSX onboarding can be claimed.
- ⚠️ Upload cap mismatch: CHAT_UPLOAD_MAX_BYTES is 25MB but the design fixes <=20MB. Enforce 20MB at the onboarding layer (a dedicated validateUploadFile/override) or the promise is inaccurate.
- ⚠️ Divergent reason minimums: org PATCH min 3, AnA viewReason min 8, GovernedActionSignoff/governed-action min 10 + distinct-char quality. Standardize the UI on >=10 so the OnboardingCommitRequest.reason passes every downstream gate; a 3–9 char reason would pass the UI-less HTTP path but fail e-sign.
- ⚠️ Tool-selection may drop a brand-new tool: stream.ts selectToolsForTurn (756) can trim onboarding_ingest by relevance unless pinned. Rely on POST /api/onboarding/ingest as the deterministic P2 backbone; treat the tool as the narrator, not the backbone.
- ⚠️ Streaming ToolContext is thin: stream.ts populates only {organizationId,userId,projectId} — no threadId/chatMessageId/ip/ua. agentAuditDetails needs threadId/chatMessageId, so the commit MUST run in the ana-ri governed-action path (CommandContext), not the SSE tool path. (And CommandContext still lacks ip/ua — plumb from HTTP or accept null.)
- ⚠️ Audit best-effort swallow: auditService.logAction is Promise<void> and swallows persistence failures (L264-267); the AnA `auditLog` named export is additionally fire-and-forget. For strict Part-11 fail-coupling use the NET-NEW logActionTx (task #16, not yet implemented, greenlight-gated); until then AWAIT logAction and order it last.
- ⚠️ projects.clientWorkspaceId AND projects.type are notNull with no default; onboarding knows only orgId. The default-workspace resolver is a hard prerequisite for any first-program commit — skipping it throws a NOT NULL violation.
- ⚠️ Org-profile writes are admin-gated: PATCH /:id/profile requires requireOrgAdmin + reason. A non-admin approver cannot commit org.* fields; run the org part of the commit under an admin actor or split org.* out of a non-admin commit.
- ⚠️ No structured tenant address column anywhere (organizations/clientWorkspaces have none; the address block at schema L910-914 belongs to supply_chain_suppliers). org.address can only land in clientIntelligenceProfiles.headquarters (single free-text line) unless columns are added — keep it documented-null-ish.
- ⚠️ ana-platform-controller.createProject (L284) is a trap: 'as any' inserts of non-existent columns, omits notNull clientWorkspaceId+type. Mirror concept2cure.ts L2089 instead or the insert fails / drops data.
- ⚠️ old_values COLUMN is hardcoded null (auditService.ts L246): before-image lives only inside new_values JSON. Any report that expects a distinct old_values column for the pre-image needs the NET-NEW oldValues threading (or logActionTx).
