# D2 AnA source access and receipt preparation

14 October 2026. Read-only preparation against the current local `concept2cure-v2` tree. This note makes no application, test, dependency, migration, provider, database or deployment change. The findings below are source inspection; proposed negative cases have not been run.

## Conclusion for the control tower

The current receipt table can support a fresh actor-authorized, source-current, bounded write of an unchanged host-admitted read span. Its existing `read_by` and `thread_id` columns can also support an explicitly actor/thread-scoped legacy coverage query. It **cannot preserve exact extraction identity or distinguish host admission, gateway submission and provider service**: those fields do not exist. Do not put an extraction digest into `content_hash`, encode metadata into `thread_id`, delete old receipts on re-extraction, or describe an ephemeral check as durable delivery proof.

The control tower selected **source actor/private-project discovery/read/recall qualification, with no schema, table or provider addition**. The selected receipt sub-slice pins org, actor, program and exact extraction in the server-owned deferred context; freshly checks that snapshot before legacy receipt insertion and the last controlled host handoff; and explicitly leaves durable rows aggregate, original-byte-bound, host-budget-admitted history. The full V2 save/export and retrieval coordinate propagation remain deferred. Options below document why stronger durable claims require additional work; they are not approval for a migration.

The narrowest no-migration increment is fresh source/project access before text or passage disclosure, revalidation at the last controlled handoff, receipt wording that says host-admitted, and optional actor/thread coverage without upgrading old receipt facts. A separately bounded prefix-reference change can store the full extraction digest in the already existing authoring provenance JSON and recheck it at save/export. That is exact **declared-source identity**, not an authentic server delivery receipt and not the broader multi-range V2 retrieval work.

If exact-extraction durable read coverage is an acceptance criterion in this increment, approve a small additive migration on `vault.document_read_receipts` and its idempotent migration-set contract first. New fields should remain nullable for historic records; new precise coverage excludes historic null/unknown fields. A full request/turn/provider receipt, multi-range references, late-table retrieval and workflow restart are separate V2 work.

## Suggested bounded contracts

### Option A: no migration, source access and truthful legacy receipt meaning

1. One canonical read-side helper receives server actor/org/open scope and query executor; calls existing persisted membership/private policy. Resolve by-ID metadata and project before fetching text. Open scope pins exact program; no open scope authorizes each disclosed project or a canonical accessible set before list/search/count/title/text is exposed. Do not implement a second sharing policy.
2. New source snapshots carry `documentId`, `programId`, original hash, full extraction SHA, exact bounds/text and availability caveats internally. Last controlled disclosure/host handoff rechecks actor/project/source and exact full extraction; a change becomes a named refusal. This is a point-in-time guarantee: no claim of authorization after later revocation, and no long-running DB lock during egress.
3. Keep whole-or-nothing budgeting and exact-string equality. Receipt settlement calls a short canonical source-current/actor-admitted writer, which rejects program/source/byte/extraction mismatches, revoked actor and out-of-bounds spans. Current extraction may be checked at insertion, but the existing table cannot later prove which extraction it checked.
4. Label persisted legacy receipt coverage as `original_record_span_history` or equivalent clear prose, `contextDelivery:'host_admitted'` only where newly issued, `extractionBinding:'not_recorded'`, and `providerDelivery:'not_established'`. Do not mint these new state fields on old rows. Preserve current legacy catalog gate only if the root explicitly chooses that compatibility scope and the UI/tool disclosures do not claim current-actor/extraction/provider coverage.
5. If adding `readBy`/`threadId` filters to coverage, use a new explicit options contract rather than silently changing all callers. Require server actor, do not coalesce null actors or null thread IDs into a claimed current scope. Surface missing coverage/refusal honestly. A query filtered to actor does not fix the same-extraction gap.

Suggested internal interface for the selected path:

```ts
interface AnaSourceReadSnapshot {
  organizationId: number; userId: number; programId: string;
  documentId: string; contentHash: string; extractedTextSha256: string;
  totalChars: number; span: { start: number; end: number };
}
// Reuses the access owner's canonical persisted policy and canonical source loader.
verifyAnaSourceSnapshot(q: Queryable, snapshot: AnaSourceReadSnapshot): Promise<void>;
// Receipt context additionally pins the exact result string/payload SHA and server thread ID.
// Host replacement/amendment must preserve a safe refusal and remove its receipt candidate.
guardPendingReadResults(original, budgeted, deferred, verify): Promise<ToolResultEntry[]>;
```

The query client must be the client used for admission and protected source reads, not a global-pool query while a transaction client is held. Check exact document/org/program, current family, disposition, live parent, actual nonblank text, catalog/source original hash agreement, full extraction SHA, true text length and strict UTF-16 span bounds. Payload values are server-pinned; inputs cannot choose the snapshot. A read refusal contains no source title, extracted text, raw SQL or internal exception.

`admitCatalogActor(...,{write:false,hold:true})` is useful for a short insertion transaction but uses project `FOR UPDATE` and therefore cannot execute inside a `READ ONLY` transaction. Its policy locks do not also reserve extraction/currentness. A writer that promises fresh source through receipt commit needs the existing disposition lock and a fixed-order source-table reservation before a fresh READ COMMITTED reload; predecessor row locks alone do not fence a successor INSERT. The root should choose and document that contention tradeoff. Dispatch guards make a fresh point-in-time check and release the transaction before gateway egress; do not hold DB locks across a model call or promise instantaneous revocation after handoff.

Both host adapters currently settle inside `executeTools`. To guard immediately before request staging, retain the round's pending receipt context until `callModel`; revalidate its exact eligible payloads, replace denied reads whole, then settle only the retained unchanged entries. If the loop halts without `callModel`, clear pending state and do not invent a dispatch receipt. The pure loop need not acquire a database/provider dependency. The source guard implementation has one owner; host adapters only orchestrate it. Even after moving the settlement location, the persisted meaning stays host admission, since a subsequent gateway refusal or ambiguous failure cannot be represented by this table.

### Option B: small additive exact-extraction receipt upgrade

Approve nullable `extracted_text_sha256`, precise receipt protocol/state marker and optional payload digest on the existing table. New writer computes/rechecks those values from authoritative source and admitted payload; a model/body field cannot attest them. Index/query precise coverage by source original hash + extraction hash + current actor (+ explicitly defined thread/history scope). Legacy null fields remain history and cannot satisfy precise coverage. Scope this to existing offset reads only; range groups, receipt IDs and request outcomes can remain V2.

Neither option alone can truthfully record provider service. Moving settlement after a successful `gateway.route` resolves budget/halt/pre-dispatch cancellation cases but still needs a gateway contract that distinguishes actual provider response from synthetic/local refusal/fallback, plus the exact final request input. A thrown/timeout/cancelled dispatch is uncertain or unconfirmed, not proof the remote provider never received it. The narrow no-migration alternative is accurate host-admitted wording.

### Optional independent prefix-reference integrity increment

Add a versioned or explicitly optional full-extraction SHA to new prefix source references and saved provenance JSON, computed from canonical stored text. Require it on newly generated source records; validate if present in public refs and retain it in verified saved refs. At save and all saved-source rendition paths compare the current full extraction digest before reconstructing the prefix. Old saved refs without the new field retain explicitly legacy byte/length identity; do not pretend exact binding or rewrite historical provenance. This adds no multi-range semantics or authentic delivery claim and should not be described as completion of V2.

## Scope ownership after root publishes the contract

Assign one canonical owner to source-admission/discovery policy. Receipt owner may own `read-receipts.ts`, an isolated receipt helper behind `document-catalog.service.ts`, and focused receipt tests; the facade itself must have a single integration owner. A different host owner can update the two settlement call sites in `AnaToolExecutor.ts` and `ana-ri/stream.ts` without editing receipt implementation. Prefix loader/reference/save/export owner can update `draft-project-sources.ts`, `draft-source-references.ts`, tool source-reference schema and focused source tests if the root selects that independent sub-slice. RAG owner owns `advancedRAGPipeline.ts`/passage adapter only after retrieval filter/currentness contract is published. Hold the full V2 table-context, multi-range, workflow-checkpoint and provider receipt architecture out of this increment.

The existing [AnA retrieval specification](../../../reports/data-room-research-2026-10-14/ana-retrieval-spec.md) is a future design dependency, not evidence of completed behavior. Preserve the completed catalog preview and prior local D2 work. Reuse existing offset budgets, source availability, family-currentness SQL, project policy, authoring transaction and disposition reservation helpers; no parallel RAG or authoring implementation.
