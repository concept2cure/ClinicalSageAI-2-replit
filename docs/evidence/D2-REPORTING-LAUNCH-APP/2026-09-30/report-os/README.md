# D2 — Reporting: the report type registry reaches a deployed database, and report runs are recorded

**Row:** D2 (Launch catalog), `docs/LAUNCH_DEFINITION_OF_DONE.md`, for Reporting &
analytics joining the catalog. This folder is the REPORT-OS part of that work.
**Date:** 2026-09-30 (runs between 2026-10-01T00:06Z and 00:26Z UTC). Working tree on
`concept2cure-v2` at `a5baf5b0`, uncommitted.
**Database:** the local provisioned test database `c2c_testdb` (PostgreSQL),
owner `postgres`, runtime role `app_service` (not superuser, no BYPASSRLS),
`RLS_ENFORCE=on`.

**What this is not:** a staging run. The migration has been applied to the local
provisioned database only, through the deploy's own applier.

## What was wrong

1. **The registry was empty on every provisioned database.**
   `report_runs.report_type_id` references `report_type_registry(type_id)`
   (`ON DELETE RESTRICT`), and `POST /api/report-os/runs` answers
   `404 Unknown reportTypeId` for a type the registry does not hold. No
   migration inserted into the registry; its only writer,
   `POST /api/report-os/taxonomy/seed`, is refused in production. On the
   provisioned test database the registry held 0 rows
   (`red/01-registry-empty-on-provisioned-db.txt`), and the real router, as
   `app_service` under RLS, answered
   `{"error":"Unknown reportTypeId: readiness.executive_digest"}`
   (`red/03-dbtest-before.txt`, third case). Every Run in the Reporting canvas
   failed on a deployed database.
2. **No report-os route wrote an audit row.** A run, a finalization (seal) and a
   PDF export left nothing on the audit trail (`red/01`, last command: no
   reference to any audit writer in `server/routes/report-os.ts`;
   `red/04-route-audit-recording-before.txt`: 6 of 8 cases red).

## What is true now

- **`migrations/20260930_report_type_registry_seed.sql`**, generated by
  `scripts/db/generate-report-type-registry-seed.ts` from `REPORT_TYPE_SEED`,
  `GLOBAL_REPORT_TYPE_SEED` and `PREDICTION_REPORT_TYPES` — the same three
  arrays, order, columns and JSON text `POST /taxonomy/seed` writes. 61 types.
  - refuses (`RAISE EXCEPTION`) when `report_type_registry` is missing: the
    table comes from drizzle-kit push, and a missing table is a provisioning
    failure (`green/06-guards-raise.txt`, part 1);
  - `INSERT … ON CONFLICT (type_id) DO UPDATE SET` every descriptive column and
    `updated_at = now()`, not `enabled`, so each deploy mirrors the code and an
    operator's disable survives (Rule 1: the file re-runs on every deploy);
  - ends with a row-count assertion that raises when fewer than 61 of the
    seeded type_ids are present (`green/06-guards-raise.txt`, part 2);
  - listed in `C2C_MIGRATION_FILES` immediately above the isolation tail.
- **`server/routes/report-os.ts`** records, with `writeChainedAuditRow`, in its
  own transaction on one connection, on the organization's chain, resource
  `report_run:<id>`:
  - `POST /runs` → `report_os.run_created`, after the run is written. The
    handler has no transaction the row could join, so when the row cannot be
    written the answer is `503 REPORT_RUN_NOT_RECORDED`, saying the run was
    created and not recorded, with its `runId`;
  - `POST /runs/:id/finalize` → `report_os.run_finalized` with the seal's
    content hash, after the seal is stored; `503 REPORT_FINALIZE_NOT_RECORDED`
    on failure, saying the report was sealed and not recorded. A finalize the
    truthfulness gate refuses (409) records nothing;
  - `GET /runs/:id/export.pdf` → `report_os.run_exported` with the SHA-256 and
    length of the exact bytes, written BEFORE anything is sent;
    `503 REPORT_EXPORT_NOT_RECORDED` and no PDF when it cannot be written (the
    same two steps as `sendAuditedExport`, which sends JSON only).
  - The 503 bodies carry a code and a sentence; the database error goes to the
    log only.

# Review round 1 (2026-09-30)

The security review found that Reporting & analytics joining the launch catalog
makes `/api/report-os` reachable in production for every organisation, which
exposes four gaps. Evidence for this round is in `review-1/`.

## 1. Finalize (DP-47)

**Was:** `POST /runs/:id/finalize` checked no role (a member sealed a report:
`review-1/red/02`, first finalize case, 200), overwrote the seal on a second
call (`red/02`, 200 where 409 is owed), and wrote its chain row in a separate
transaction after the status write — so a 503 left the run final and sealed
(`red/03`: the round-0 shape, reproduced by mutation, leaves
`{ status: 'final', seal_hash: … }` after the 503).

**Now** (`server/routes/report-os.ts`):

- `requireRole('owner', 'admin', 'manager')` (server/middleware/auth.ts, the
  canonical org-role guard) on the route: 403 before any read
  (`review-1/green/01`: member and viewer refused, zero facade reads, no
  connection opened; `green/02`: a member on the real database, nothing sealed).
  Not `canReadAuditTrail`: that also admits platform administrators, and the
  brief is owners, admins and managers only.
- A run already final → `409 RUN_ALREADY_FINAL`, checked on the read and again
  under a row lock (`SELECT … FOR UPDATE`) inside the transaction, so a
  concurrent finalize that committed first is refused, not overwritten.
- `finalizeOnChain`: BEGIN → `setTenantContextTx` → locked re-read → status
  update → seal merged onto the latest snapshot → `writeChainedAuditRow` →
  COMMIT, on one connection. A chain row that cannot be written rolls all of it
  back: `503 REPORT_FINALIZE_NOT_RECORDED`, "The report was not finalized …
  Nothing was changed." Shown on the real database with a trigger that refuses
  the row (`green/02`, second finalize case: status still `completed`, no seal,
  no row) and, by mutation, failing when the writes commit first (`red/03`).
- Every other chained row (run created, run export, bundle export) is now also
  written on a tenant-stamped transaction (`inTenantTransaction`).

## 2. Bundle export (DP-50)

**Was:** `GET /bundles/:bundleId/export.pdf` skipped the run export's
entitlement gate and wrote no chain row (`red/01`, `red/02`).

**Now:** `bundleExportRefusal` — the run export's gate over every report type
in the bundle, each decided with its registry family at the tier the gate
resolves; 403 names the first type above the plan. Then `sendRecordedPdf`, the
same step the run export now uses: `report_os.bundle_exported` (resource
`report_bundle:<bundleId>`, with the SHA-256 and length of the exact bytes) is
written before anything is sent; 503 `REPORT_EXPORT_NOT_RECORDED` and no PDF
when it cannot be (`green/01`; `green/02`, last case, on the real database).

**`POST /deliveries` with `platform_send` — not done; reported.** Nothing leaves
the platform on that channel: it writes a `c2c_correspondence` row through
`persistCorrespondenceToPlatform`, which swallows its own failure
(`catch { return { persisted: false } }`), and the delivery then reports
`status: 'sent'` whether or not anything was written. Recording "sent" before
that write would put on the chain an act the handler cannot confirm. The honest
fix is the correspondence row, the delivery record and the chain row in one
transaction, with `sent` only when the row was written — more than a few lines,
touching `persistCorrespondenceToPlatform` and `persistDeliveryRecord`.
