-- ── The regression this fix caused, and the defect underneath it ──
--
-- Making the writes succeed turned them into real work, and real work exposed a
-- latent hazard in the Module 3 compile route. Measured, CMC staff simulation:
--
--   baseline (no fix)                     : 118 passed, 0 failed
--   fix, ledger write suppressed          : 118 passed, 0 failed
--   fix, ledger write active, pool max 20 : 114 passed, 4 failed
--   fix, ledger write active, pool max 60 : 118 passed, 0 failed
--
-- All four failures cascaded from one compile. Captured from pg_stat_activity:
--
--   pid=1787 st=idle in transaction x_age=29.9 wait=Client/ClientRead
--     :: SELECT count(*)::int AS n FROM submission_leaves WHERE sequence_id = $1 ...
--   pid=1755 st=active            x_age=29.8 wait=Lock/transactionid
--     :: INSERT INTO cmc_module3_sections (organization_id, project_id, section_key, ...
--
-- POST /api/cmc/module3-os/compile/:projectId opens a transaction on a dedicated
-- client, then calls composeProjectModule3 -> resolveProjectRegionCode ->
-- resolveSubmissionSpine, which reached for the SHARED pool. That second
-- connection is the hazard: with the pool saturated the read waits, the
-- transaction sits idle holding its locks, a concurrent compile's INSERT blocks
-- on its uncommitted rows, and the 30s statement_timeout cancels it.
--
-- Raising the pool ceiling hid it. The fix removes the second connection:
-- resolveSubmissionSpine now takes the caller's Queryable, so the reads run on
-- the transaction's own connection and see its own snapshot.
--
--   fix, ledger write active, pool max 20, spine on the caller's client
--     : 118 passed, 0 failed   (decision_records 248 -> 280)
