# g-in-text-reference-resolution — facts relied on

Step: a cross-reference grounds a claim only if it resolves. Checked 2026-10-05.

The classifier does not hold its own copy of any regulator tree. It walks the
platform's canonical trees: ICH E3 in `server/services/ind/ctd/csr-e3-guidance.ts`
(`getE3Section`, `e3ParentNumber`, `e3Children`) and the CTD authoring registry
behind `getCtdAuthoringGuidance` (`listCtdGuidanceCodes`, `server/services/ind/ctd/index.ts`).
So most facts below are the basis of a tree the platform already relied on.
There is one exception, added in fix round 1: row 5's ICH M4 child counts. The
module now holds these counts (`CTD_M4_CHILD_COUNT`) so that it does not treat
an incomplete registry as complete. They are recall.

## What the step asked for and I did not do, and why

- **The leaf set via `resolveCrossReferences`.** No caller holds a package leaf set at critique time. The gate is pure, and `check_ectd_cross_references` already does leaf resolution. `resolveCrossReferences` matches only an exact section, key or file, so a parent-code citation ("Module 5.3.5" against leaves 5.3.5.1…) would be reported broken. Added to needs_elsewhere for whichever caller first has both.
- **The zero-duplication migrations** of `harmonize-engine.ts:308-360` (checkReferences) and `claim-evidence-engine.ts:67` are outside this step's file list. They are in needs_elsewhere.
- **Scope.** Only references on quantitative-claim sentences are classified. That is the grounding dimension's scope. A broken reference with no number on it is not reported by this step.
- **The M4 child counts belong beside the registry.** `CTD_M4_CHILD_COUNT` lives in `in-text-references.ts` because `server/services/ind/ctd` is outside this step's files. Registering 2.5.7, and moving the counts beside the registry as a per-heading `complete` assertion, is in needs_elsewhere. When 2.5.7 is registered, 2.5 becomes complete with no change here.
