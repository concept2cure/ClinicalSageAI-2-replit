── Three screens have nothing to operate, honestly ──────────────────────────
Not every blank is a gap. Each of these was read in full and left empty:

  dispatch-readiness   Submission Readiness is a verdict, not a workspace. The
                       component imports `React, { useMemo }` and holds no
                       state at all — no tabs, no filters, no selection. Its
                       two buttons both call ask(), handing a proposal to AnA
                       in conversation, and the transmit stays behind a Part 11
                       e-signature. She already publishes the whole gate as
                       context, so she can explain every blocker on arrival.
  part11-console       Same shape: a compliance read-out with no view state.
  setup                A launcher.

A LATENT TRAP found while checking this, worth writing down: every action id
is namespaced `<surfaceId>.<verb>`, and GOVERNED_VERB_PATTERN matches
`dispatch` on a word boundary — which `dispatch-readiness.` satisfies. So
`dispatch-readiness.anything` is refused as governed work, by
assertUngovernedActionId at build time and resolveSurfaceAction at runtime.
Verified against the real exported pattern. A future session that adds a
control to that screen will hit a build failure, not a review comment; it will
need the nav target renamed (`submission-readiness.*` passes cleanly) or the
pattern taught to distinguish a surface prefix from a verb.

Honest refusals, as the rest of the bus does them:
  - held (`retry: true`) while the ledger is in flight, answered by the ready
    signal when it settles;
  - a failed read says "the hash-chained ledger could not be read … that is
    not the same as the trail being empty" — an empty table must never read as
    an empty ledger;
  - a filter that matches nothing still applies and reports its real count;
  - a miss on an entry lists the ids that ARE on screen, so she can retry.

The ready signals are gated on the read settling and nothing else, which the
existing guard (surfaceReadySignal.test.ts) enforces across every screen.

── The harness, against the redesigned shell ────────────────────────────────
Upstream landed ~2,000 commits between the last pass and this one, including
the conversation-first shell convergence. Three things moved, and the battery
was repaired for each (no product defect in any of them):
  - the persistent AnA rail is gone. A working screen now carries an "Ask AnA"
    control that goes to the conversation destination; the old `railAsk`
    scenario is now `askFromScreen`, which checks the entry point exists, the
    ask still drives the screen, and the answer survives the move. Not every
    screen carries the control (the audit trail does not), so the harness
    falls back to the conversation destination.
  - a conversation now has its own path segment
    (/concept2cure/conversation-thread/<threadId>), so paths are compared by
    prefix.
  - a long demonstration virtualises, so the rendered tail no longer holds
    every stop. The narration check reads the conversation's saved message —
    what the person scrolls back to — instead of the visible tail.
Re-verified on the merged tree: Live Drive navigation reaches Biostatistics in
2.8 s, and the training demonstration narrates all 14 of its stops (it gained
two upstream), each in its own paragraph.

Also needed before any of this would run: the local database was 12 days
stale and login failed outright against it (`public.user_id_for_email` did not
exist). `npm run db:migrate:deploy` fixed it.
