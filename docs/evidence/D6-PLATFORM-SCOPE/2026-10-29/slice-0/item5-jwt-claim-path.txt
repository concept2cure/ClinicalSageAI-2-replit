A. Where the role a request scope sends is decided

The setting is written by the pool from TenantScope.role:
  poolInstrumentation.ts tenantSetConfigSql
  sessionScope.ts applySessionScope

No layer filters the value 'app_super_admin':
  server/middleware/establishRequestTenantScope.ts  role = String(req.user.role), passed to tenantSessionVars and runWithTenantScope
  server/db/sessionScope.ts  applySessionScope writes scope.role verbatim
  server/db/poolInstrumentation.ts  scopeParams writes scope.role verbatim

Where req.user.role comes from, by authenticator:
  1. server/auth.ts:296 (the global /api gate, authMiddleware)
       organization_users.role, read on this request for (userId, organizationId).
       Filtered by the database row, not by the token.
  2. server/middleware/auth.ts:254 admitLiveSession (authenticateToken)
       Starts as decoded.role || 'user' (the token's claim).
       applyOrganizationRole (:320) replaces it with the membership role before establishRequestTenantScope runs (:295).
  3. server/middleware/tenantContext.ts:333 (requireTenantContext)
       organization_users.role (resolvedRole).
  4. server/middleware/auth.ts:644 optionalAuth
       decoded.role. It opens no scope itself.
  5. server/routes/authoring.router.ts:234-238
       role: decoded.role, the token's claim, VERBATIM.
       enforceOrgMembership (server/middleware/orgMembership.ts:351) sets req.user.organizationRole, not req.user.role.
       So req.user.role stays the claim, and :8276 (the image upload) re-enters
         runWithTenantScope({ role: req.user.role })
       which sends the claim to app.current_user_role for that upload's statements.
       The ONLY verbatim claim-to-database path found.
  6. vault-ingest.ts:229, moduleIntegrationRoutes.ts:493

D. The database's own guard
  organization_users_staff_role_platform_only refuses a staff role (super_admin, superadmin, platform_admin,
  app_super_admin) outside the platform scope. It decides by reading app.rls_enforce and app.current_user_role.
  Measured (item5-role-claim-db.txt):
  - An ordinary admin scope is refused.
  - A scope whose role string is 'app_super_admin' writes it onto its own membership. This works WITH the P arm and
    also with it removed, because the trigger reads the setting in its body.
  - So a session that carries the string once can make it durable, and every later sign-in mints it (B).

E. Conclusion
- No assignable role and no minting route produces 'app_super_admin' today.
- One route (authoring.router.ts:238 / :8276) carries the token's claim, not the current membership, to the database.
  A claim is a stale copy of the role at sign-in.
- Nothing between the request and the database refuses the literal. The trigger that stops minting it is itself
  switched by the setting.
