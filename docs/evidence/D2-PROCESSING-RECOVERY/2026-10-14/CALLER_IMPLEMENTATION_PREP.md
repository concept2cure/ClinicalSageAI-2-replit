## Shared API needs

The core owner proposed an additive `processCapturedSource` result `{ ok, processed, status, reasonCode?, extracted? }`, with `ok` and `processed` true only for a committed readable stage or an already complete readable stage. Optional `preExtracted`, explicit workspace scope, executor injection and retry policy are pending the published contract.

The processor should load and bind the recorded original upload itself, compare source and upload digest/scope/availability/currentness, and enforce that identity again at the derived commit. A repeated chat upload creates a **new** upload ID before checksum lookup. Its new ID must never replace the existing source's original upload provenance merely because the bytes match. A verified duplicate can supply same-byte input while the processor retains and verifies the original binding. Historical or withdrawn sources must not be revived or written. A stale source outcome must be visible rather than converted into a new successful capture or silent retry.

The [shared upload hook](../../../../client/src/concept2cure/hooks/useChatUpload.ts#L203) treats HTTP success as attachment availability and marks it `ready`; it does not consume Data Room processing. Preserve that compatibility. Add `dataRoom.processing`/readability fields to the route response rather than redefining top-level `ready`. Current `extractionMethod` and word counts describe the current extraction attempt; they must not be presented as evidence that catalog text/facts committed.

## Fail-first caller fixtures

1. Real multipart chat route: newly captured source is pending until the processor completes; false, failed, stale and thrown processor outcomes preserve stored capture and return an honest processing state. Scanner/storage/project refusals remain before all downstream effects.
2. Chat checksum duplicate: an unfinished source is sent to the processor with the same source ID and project/workspace scope; new upload ID is absent from any existing-source rebinding. Already complete returns readable without another capture. Historical/withdrawn returns stale and no readable claim.
3. Real adoption route: after the capture/audit COMMIT, failed or thrown processing returns adopted=true, processed=false and recovery state. Duplicate adoption rolls back its empty capture transaction, performs safe recovery and returns adopted=false plus canonical processing, with no second source/audit capture.
4. Spreadsheet service: after source/edit-receipt COMMIT, failed/stale/thrown processing returns captureStatus=captured plus processing state; no rollback cleanup deletes committed derived bytes. Conversation-only edits never call CRE processing. Successful processing returns readable while scientific qualification remains unassessed.
5. Existing SQL eligibility/lineage suites retain real SQL, withdrawal, byte identity and atomicity coverage. Make processing an explicit seam where their fixture lacks the processor's source/catalog schema; do not rely on incidental incomplete-schema errors as proof of pending state.

Target suites: [chat-upload-durability](../../../../server/routes/__tests__/chat-upload-durability.test.ts), [projects-adoption](../../../../server/routes/c2c/__tests__/projects-adoption.test.ts), [projects-adoption-sql](../../../../server/routes/c2c/__tests__/projects-adoption-sql.test.ts), [derived-spreadsheet-capture](../../../../server/services/ana/__tests__/derived-spreadsheet-capture.test.ts), and [derived-spreadsheet-sql](../../../../server/services/ana/__tests__/derived-spreadsheet-sql.test.ts).
