# Independent SQL interpolation review

The nineteen files reported by the first canonical push contain no observed interpolation of a client, model, source, tenant, digest or other external **value** into SQL text. The added expressions are fixed server-owned SQL structure: predefined policy predicates, projection/column/table names, finite literal clauses, and internally generated `$n` placeholder indexes. Actual values remain in bind arrays. `SQL_INTERPOLATION_CHIEF_REVIEW.json` records each exact source hash, count transition, expression locations and traced provenance. This is a read-only review; this owner changed no application source, baseline or gate.

The gate deliberately counts syntax rather than proving data flow. Its own header recognizes safe generated placeholders and code-constant table names, and permits a genuine identifier from a fixed allowlist with a documented baseline increase. Its final output and pre-push comment say the baseline only shrinks; that slogan does not remove the more specific documented allowlist exception. The proposed resolution must use the existing exception transparently: update only these nineteen audited counts, retain the five-to-zero decrease, and describe the fixed structural provenance in the commit and evidence. A generic statement that SQL is “safe” is insufficient. No whole-baseline regeneration, scanner change or query rewrite that hides a call in a variable is warranted.

The two lead-owned additions are particularly narrow:

- `document-data-disposition/service.ts` moves from one to two counted expressions. The existing expression joins the module-private `IMPACT_TABLES` identifier list. The addition selects only `''` or the literal ` AND deleted_at IS NULL FOR SHARE`; program and organization remain `$1/$2`. It cannot splice a role, reason, source identity or caller-chosen clause into SQL.
- `tenant-export/tenant-full-export.service.ts` moves from eight to nine. The addition selects only `''` or literal ` FOR SHARE`; organization and digest remain bound. Existing identifiers come from catalog discovery constrained by fixed schema/key-column sets, then pass the identifier regex and are quoted separately. Existing scoped predicates and row cap are code constants. The new hold clause does not expand that existing identifier contract.

For a strictly identifier-only interpretation, each optional hold query can be expressed as two explicit `.query()` calls with static SQL literals, one with the lock clause and one without. That preserves the statements and keeps both calls visible to the gate. It changes application code and requires fresh source qualification; it offers no injection protection over the present two-literal choice. Parameterizing `FOR SHARE` as a value is not valid SQL, and making every lookup lock unconditionally changes behavior.

The other sources follow the same concrete boundary. Receipt history generates only placeholder numbers while optional IDs enter `params`. The receipt store's projection and assembled INSERT are fixed literals; its sixteen descriptor fields are bound. Processing uses fixed JSON field names, fixed aliases, code enum labels and predetermined stage predicates; source IDs, limits, metadata, facts and text are bound. Search uses fixed column maps and policy helpers, generated placeholder indexes, and bind values for query text, program arrays, dates, thresholds, vectors and pagination. Capture reads use literal projection/join/scope factories. Catalog raw-query extraction moved genuine query calls into their new helpers; lowering `document-catalog-search.ts` from five to zero is appropriate and must accompany the new helper's audited count.

The audit also inspected assembled queries the unchanged gate cannot see, including the receipt INSERT and processing sweep's main query. No statement was moved or obscured for this review. Dependency hashes cover policy/lineage predicates, version predicates, processing field/enum factories, filter-column maps and the original gate/selftest. The scanner's nested-template and assembled-string blind spots remain known limits; this review does not claim a whole-platform SQL injection qualification.

Recommendation: accept the narrowly documented structural exceptions after the disjoint owners' audits agree, update only the nineteen exact counts in the JSON, retain the gate and selftest unchanged, and rerun both gates before pushing. No production defect requiring an application rewrite was found in this bounded review.
