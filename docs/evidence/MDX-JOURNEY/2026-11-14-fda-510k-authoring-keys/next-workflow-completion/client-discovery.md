## What already exists

- `client/src/concept2cure/v2/useVaultUpload.ts` is the shared ingestion owner, currently called by `mdx/surfaces/pathway/DossierAttachments.tsx`, `v2/surfaces/Vault.tsx` and `v2/surfaces/VaultTmfFiling.tsx`. The old MDX VaultSurface is not a current caller. Uploads are sequential and strict committed receipts are parsed by `v2/vaultIngestReceipt.ts`; transport remains `v2/vaultIngestTransport.ts`.
- `readVaultIngestReceipt` verifies HTTP200/201, actual UUID, exact requested program UUID, document code, reupload semantics and placement consistency. The returned `document.id` is the concrete Vault document/version UUID; its textual version is separate. A governed dossier's `documentId` is a different namespace (`c2c_documents.id`, commonly `doc_<hex>`), not necessarily a UUID.
- `VaultUploadOutcome.recorded` contains UUIDs only for confirmed successes, in success order. It is compressed when earlier selections fail. `succeeded`, `filings`, `alreadyRecorded` and `failed` similarly lack original-index identity. `onFileStatus(index,status)` already supplies the original selection index, but its stored status currently discards the actual UUID even though `uploadOne` has it. This is the smallest appropriate receipt extension point.
- `v2/vaultUploadVisit.ts` owns session/program/optional caller-key lifetime and a synchronous batch ticket. It uses canonical authoring-session authority and adopted-bearer checks, retaining normal same-account refresh semantics. It retires a changed program prop/key/session on render, protects queued dispatch and suppresses stale callback/result delivery. A duplicate `begin` is refused synchronously. Cleanup is currently passive; no shell guard is captured here. `attempt.current` becomes false when `finish` clears the ticket, so it cannot currently authorize a later governed link operation. There is no public live completion predicate on outcomes.
- `mdx/surfaces/pathway/DossierAttachments.tsx` is the extracted existing UI owner. It captures scope `[programId,documentId,pathway,section id,label]`, a monotone component generation and `captureShellProjectGuard`; it keeps upload feedback alive while another drawer tab is shown. It collects stored **indices** in a Set, so same filenames are not correlated by name. After upload it requires current drawer/session plus at least one confirmed outcome, then calls local `DossierStore.attachFile` for those indices. It discards the UUIDs and creates no durable association.
- That caller currently performs only one guard before its `forEach`, not before each local write. Its scope does not include the actual hydrated meta object. A same-document rehydrate can therefore replace the cache without changing scope, and synchronous subscribers between writes can change the insertion target. It does not require the actual shell program UUID to match props, or an exact hydrated document/section before uploading. Component cleanup is passive. These matter before adding another awaited write.
- `mdx/hooks/useDossier.ts:121` reads the exact project/document class, outline, and content only for sections with `has_content`. Every section is explicitly returned with `attachments: []`, so any local association disappears on refresh or reload. Its existing session-keyed query owner distinguishes denied/unavailable/empty states and revalidates on mount. Hydration and clearing happen in a passive effect.
- `mdx/types.ts:285` defines `DossierAttachment` with only name, mandatory numeric size, kind, mandatory who/when, optional source/live. It cannot represent a durable link ID, exact source UUID, source version, nullable recorded metadata or server attribution.
- `mdx/store/dossierStore.ts:154` builds local attachments, inventing `who: 'You'`, browser time, zero size and `Sources/uploads/` when absent. It correctly creates no client audit event. The server owns actual upload audit. `hydratePathway` already accepts attachment arrays and replaces the cache; extend that projection rather than create another store. `clearPathway` currently clears files but leaves `backendDocId` cached; exact authority must also require installed section metadata, not that map alone.
- `mdx/surfaces/pathway/FilesTreePane.tsx` builds attachment identities as folder/name, so distinct source versions sharing a filename collide. Its download action is `href='#'` with `preventDefault`, so it downloads nothing. It labels `who` as Uploaded by even though current data is browser attribution. The memoized tree omits the store epoch despite its subscription forcing rerenders; local attachment notifications alone do not rebuild its cached tree. A selected cached node also carries its own old metadata.
- `server/routes/c2c/documents.ts` already has POST/DELETE evidence routes over `c2c_document_section_evidence` and atomic governed audit. Current writes now check project edit right, but still lack a verified exact Vault reference, retained source/filing/authoring seals and outcome-unknown semantics needed before wiring the client. There is no evidence GET/hydration in the current client. The existing GET outline and GET section routes can carry authoritative link projections without adding a route mount; backend design must decide the contract.
- Current original download authority already exists: `GET /api/c2c/project-vault/:programId/documents/:documentId/download`. `v2/surfaces/Vault.tsx:1593` uses authenticated `apiRequest`, then `downloadBlob` from `v2/download.ts`. The server checks program/tenant/document, retained availability and stored-byte hash, and audits before release. Reuse that route and browser primitive. Do not invent an exporter or download by filename.

Searches covered upload receipt/status/outcome and all live callers, MDX store/types/hydration/tree/drawer, evidence routes, authenticated downloads, current tests and coordination. A deleted-path search found no matching removed owner in fetched history; the checkout remains shallow, so historical absence is not exhaustive.

## Minimal data and lifetime contract

1. Add the exact `documentId` to the existing **stored** `VaultUploadFileStatus`; `onFileStatus` already supplies original index. DossierAttachments can capture `Map<originalIndex,confirmed UUID>` (plus the existing version field) instead of correlating names or zipping `recorded` with selected files. Preserve compressed legacy outcomes for current callers. Strict receipt parsing remains unchanged. No UUID is inferred from a filename, array position among successes, program ID or governed dossier ID.
2. For a workflow that awaits another write after ingestion, extend the existing upload owner with a live original-attempt predicate that remains usable after normal finish, retires on the next admitted attempt/visit/session and cannot revive after A→B→A. Nonadmitted duplicate calls must not invalidate the active attempt or clear its state. An additive outcome predicate and/or callback predicate is preferable to a second uploader/lifetime implementation. A caller exact-target predicate, checked before each dispatch and result, must retire monotonically. Existing visit cleanup should cover the layout/unmount boundary if retained native callbacks can run before passive effects.
3. Preserve canonical session behavior: `captureAuthoringSession` intentionally compares actor/org/access scope and session revision, not raw account-object identity, and allows ordinary adopted refresh. Pin each request's headers to the captured actor using existing `capturedActorHeaders`; `uploadOne` currently rereads generic `getAuthHeaders`, so a synchronous callback changing actor between its current check and transport dispatch can send a replacement actor's headers to the original program. Do not change the strict parser or bypass its auth gate.
4. Bind the drawer operation to exact program UUID, dossier document ID, pathway, section key/label, actual installed meta-object identity and backend document mapping, plus captured session and shell visit. Require hydrated matching data before admitting attach. Check before every server mutation and every cache write; synchronous store subscribers can invalidate a batch between writes. A composite caller lease should cover ingestion **and** linking, since ingestion's own lease finishes before the second phase. Tab switches within the same open drawer should preserve feedback; close/unmount/retained callbacks must retire through existing owners.
5. For each confirmed index, call the existing governed section-evidence writer with the exact source version UUID and a deliberate reason. This is a second independent commit: a link refusal does not undo the confirmed Vault upload. A malformed successful link receipt, lost acknowledgement, transport failure or typed OUTCOME_UNKNOWN cannot become “nothing was saved”; retain a hold, offer authoritative current-link/audit review, and never reupload automatically. Do not promise the drawer Activity tab proves links: it reads content-version history only.
6. Validate the link receipt/read projection against the original dossier ID, section key, program/source UUID and durable link ID before showing it. The backend must return actual server linked-at/linked-by attribution and the exact source-version metadata. Missing actor/size/time stays unknown, not You/zero/browser now. An already-held link returns its original link ID/attribution and should not produce duplicate local rows or a fabricated new event. Same bytes selected twice can map to one retained version and one existing association; distinct same-name UUIDs remain distinct.
7. Extend `DossierAttachment` and the existing store's hydration/projection to retain durable link ID and concrete source-version identity. Keep the store a display cache; do not add local persistence or a second evidence ledger. Avoid fallback source paths or fabricated upload attribution for durable rows. Old local-only rows cannot be promoted into persisted links by assumption.
8. Hydrate links for **all** outline sections, including empty body sections. Preferred minimal API shape: extend the existing outline response with per-section evidence arrays under the current admitted document read. If backend chooses existing section GET instead, fetch it for empty sections too; current `if (has_content)` would lose links. Do not turn denied/unavailable/malformed evidence into an empty list or erase the server association. Current exact document/session ownership must still govern publication.
9. Replace the fake Files-tree link with the existing authenticated version download. Use concrete source UUID and original program, never current filename lookup or automatic newest-version replacement. Pin actor/session/shell/hydrated target at dispatch and check again after both HTTP and Blob awaits before `downloadBlob`. Existing `apiRequest` accepts custom captured headers and an AbortSignal; it intentionally returns401, so mutations must also check success explicitly. Current read retirement must not let an old401 terminate a newer session.
10. Tree paths/React keys/selection must use durable link identity, with display names separate; update the store epoch in the memoization dependency and retire or reacquire selected nodes after hydration/unlink. Unknown source size/date/actor must render honestly. The existing native controls and inline ErrorState/feedback are the UI owners; no new page or card is needed.
