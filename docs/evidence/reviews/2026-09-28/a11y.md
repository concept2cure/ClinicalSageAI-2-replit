### Why A-0928-1 is rated a blocker and not advisory

This is not the same shape as the app's widespread (and pre-existing, not newly introduced) pattern of a visual-only `*` beside a label — that pattern already exists elsewhere (`CmcModule.tsx:2104`, `Surfaces.tsx:788`, and the pre-existing "Section code" field in the very same two dialogs). What is new and materially worse is: (1) the section-code field this pattern normally accompanies always renders a *visible*, `aria-describedby`-linked note the instant it has anything to judge (`AuthoringPlaceIntoFiling.tsx:366-376`), so a screen-reader user gets the requirement without needing the field to already be wrong — the new reason field does not, staying silent about "required" until you've already typed and failed; and (2) the disabled-submit-button explanation, which is the *only* other channel, is behind `title`, which native `disabled` buttons remove from the accessibility tree's operable path entirely (no focus, so no way to reach the tooltip by keyboard). No test in `client/src/concept2cure/v2/__tests__/` references `PlacementReasonField` or `placementReasonOk`, confirming this shipped with no accessibility check.

### A-0928-1 — **confirmed**

I tried to refute this at aff7eae16 and could not. The defect is real, but "blocker" overstates it. It is a major or advisory issue under WCAG 1.3.1 and 3.3.2 (plus 4.1.2 hygiene).

What the code shows:
- **The field is not marked required.** In `client/src/concept2cure/v2/surfaces/filingTarget.tsx:355-373` (PlacementReasonField, added in fc29f2d1c PX-1), the `<textarea>` has neither `required` nor `aria-required`.
- **The asterisk is part of the field's name.** Line 356 puts `<span className="req">*</span>` inside the `<label>` with no `aria-hidden`, so a screen reader announces the name as "Reason for this placement star".
- **The requirement is never stated before typing.** The `aria-describedby` note (lines 369-372) says "At least 8 characters." only when `short`, which needs `value.trim().length > 0`. With the field empty it says "Recorded with the placement in the audit trail." The note also has no `aria-live`, so the text change is not announced while the user types.
- **This breaks the repo's own convention.** The shared form at `client/src/concept2cure/v2/C2CForm.tsx:130` sets `'aria-required': f.required`. At lines 211-222 it marks the asterisk `aria-hidden="true"`, and its comment says why: so a field is not read as "Method code star". PlacementReasonField does neither.

All three forms are reachable in the launch catalog:
- **Authoring:** AuthoringPlaceIntoFiling is mounted from `editor/DocumentCanvas.tsx:355` and `editor/DocumentWorkbench.tsx:3389`.
- **Vault:** VaultPlaceIntoSubmission, `VaultPlaceIntoSubmission.tsx:358`.
- **Submission Center:** the add-leaf form in `SubmissionSeqWorkspaces.tsx:420`.

The disabled Place buttons:
- **Vault and Authoring:** the only explanation is a `title` on a native `disabled` button (Vault via `placeBlockedReason` at `VaultPlaceIntoSubmission.tsx:83-96`, rendered at 370-373; Authoring at `AuthoringPlaceIntoFiling.tsx:440-449`). A disabled button cannot take keyboard focus, so a keyboard or screen-reader user never reaches that tooltip.
- **Submission Center:** the button at `SubmissionSeqWorkspaces.tsx:421-427` has no `title` at all.

Nothing else in the code states the requirement accessibly. The Authoring dialog's `role="status"` blocks cover only the unsaved-changes warning and the post-placement result.

Why this is not a blocker: the flow can still be completed. The field is labelled and reachable by keyboard. The spoken "star" hints that it is required. Once the user types something too short, the note on the field (read when it has focus) says "At least 8 characters."

Scope note: the same pattern (asterisk, no `aria-required`) already exists on the "Section code" fields at `VaultPlaceIntoSubmission.tsx:132` and `AuthoringPlaceIntoFiling.tsx:356`. So this is a repeat of an existing gap, but the new field adds its own instance of it.
