Full evidence, the false sentence a user would read, and the two-option fix are in the finding record.

No other concrete, reproducible honesty defect was found in this scope: fixture usage is nonexistent (only one `import type` from `fixtures/protocol-data` for a TypeScript interface, no runtime data), no `useLive`/`liveGet`-style fixture-fallback pattern appears (this family uses `apiRequest`/`apiCall`/`useLiveData`, the fixture-free hooks), every write path (`ProtocolDevWrites.ts`, `ProtocolRegisterForms.tsx`) throws on refusal and only reports success after a confirmed 2xx with the server's row, and every failed-read branch I traced (`AuthoringExports`, `ReviewThreads`, `ProtocolDevDerivation`, `ProtocolDevDesign`, `ProtocolDevProjections`) renders a distinct error state rather than collapsing into an empty one.

## Independent verification

Each finding went to three agents, each told to refute it through one lens: reachability, reproduction or intent. A finding is confirmed when two of the three could not. Low findings had one reproduction verifier.

### GP-H-1 — **refuted** (0 of 3)

- **reach** — not real: Checked at the working-tree HEAD, 494b4fc14. The task named 232ecae9c, but that is an ancestor, and none of the files involved differ in a way that matters.

The client code is as the auditor describes. `ConsentTab` (client/src/concept2cure/v2/surfaces/ProtocolDevReviews.tsx:117-134) only guards `!form || consent.length === 0`, then computes `Math.round((present / required.length) * 100)`. The data comes from pdev-view-assembler.ts:576, which forwards every `consent_form_elements` row with `required: bool(e.required)`. The tab is mounted at ProtocolDevWorkspace.tsx:236.

The state that would trigger the bug cannot be produced through the application. It needs a consent form whose elements are all `required = false`, and no write path creates or reaches that state:
1. Every row is inserted in one place, `createConsentFormTx` (server/services/protocol-consent/protocol-consent-service.ts:48-66). It always seeds the fixed `consentElementTemplates()` set (protocol-consent-logic.ts:29-44), which has 9 elements with `required: true` (45 CFR 46.116(b)(1)-(9)) and 6 with `required: false`. The caller cannot supply or override the element list or the `required` flags. Both entry points go through this function: POST /api/protocol-consent/forms and the AnA tool `create_consent_form` (AnaToolExecutor.ts:11068-11072, which imports `createConsentFormTx`).
2. The only update statement is `updateElementTx` (service:89): `UPDATE consent_form_elements SET content = COALESCE($3, content), present = COALESCE($4, present)`. It never touches `required`. The PATCH /elements/:id schema (routes/protocol-consent.ts) accepts only `content`, `present` and `reason`.
3. No route or service deletes elements, and no DELETE statement anywhere in server/ targets `consent_form_elements`. The migrations do not seed the table: grep found only the table definition in migrations/20260629_protocol_consent.sql (line 41, `required boolean NOT NULL DEFAULT true`) and no INSERT.

So any form that reaches the assembler with `consent.length > 0` has `required.length >= 9`. The division is never 0/0, and "NaN% complete" cannot appear without direct database tampering, which is outside the application's threat surface. With at least 9 required elements, the client's ratio is the same number the server engine would give. The duplication point is a design or zero-duplication concern, not a reproducible failure a user, auditor or attacker can hit.

Covered: the ConsentTab source, the assembler's consent mapping and query, every writer to `consent_form_elements` in server/, migrations and scripts, the REST routes and the AnA tool path. Not covered: I did not exercise it against the local Postgres, because no write path produces the state, and I did not check whether the ProtocolDev surface is registered in the launch-catalog navigation.

The guard at client/src/concept2cure/v2/surfaces/ProtocolDevReviews.tsx:120 (`!form || consent.length === 0`) also does not catch `required.length === 0`. (1) The only code that inserts rows is createConsentFormTx, in server/services/protocol-consent/protocol-consent-service.ts:48-66. (4) In the reference database c2c_full, `SELECT ... GROUP BY consent_form_id HAVING count(*) FILTER (WHERE required)=0` returns no rows, and the table holds 0 rows.

"A form built only from 46.116(c)/(d) additional elements" cannot be created through the product. The NaN branch is reachable only through direct SQL, so no user, auditor or attacker using the application can hit it.

The duplication point (the client recomputes a ratio instead of consuming evaluateConsentCompleteness) is a real code-quality observation. It is not a demonstrable failure for the stated scenario.

One side observation, not part of GP-H-1 and not verified in the UI: the two calculations use different rules. ConsentTab counts `present` only. A required element marked present with blank content therefore raises the tab's percentage, while the approve gate still refuses the form. That is a separate candidate finding and needs its own reproduction.

On the duplication charge: the client computes a display ratio from the rows the server sends. In every reachable state, round(present/required*100) equals the server's requiredPresentPct. It is not the model producing a figure, and it gives no verdict that disagrees with the server. The BudgetTab precedent involved a real divergent re-derivation (F&A, margin).
