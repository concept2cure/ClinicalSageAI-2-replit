# Tenant retention integration — 2026-10-14

## Behavior and remaining limit

Tenant offboarding now refuses physical erasure when the requested organization holds controlled QMS versions or frozen submission inputs. These stores contain actual signed prose, legacy registry metadata, or private original input/output content; they are not classified as content-free audit receipts. The organization remains pending deletion and exportable until governed retention review establishes an approved disposition path. This implements a safe, truthful refusal; the requested erasure policy remains partial.

The new preflight runs on the existing purge transaction client before any erasure door, row deletion, organization status change, storage deletion, or purge-success audit write. It locks the requested organization `FOR UPDATE`, verifies the current state, requires both stores to exist and be readable, and checks only org-scoped `EXISTS` values. It fetches no prose or input body. Table absence, read refusal, or malformed check results yield `REGULATED_RETENTION_CHECK_UNAVAILABLE`; actual retained content yields `REGULATED_CONTENT_RETENTION_REVIEW_REQUIRED`. The existing operator route maps these actionable refusals to HTTP 409. A retention-window override cannot override this content gate.

Both immediate organization foreign keys acquire insertion key-share locks. The purge's organization lock waits for already-in-flight insertions, then performs a fresh retained-content read and remains held through the transaction. New canonical writes to pending-deletion tenants remain refused by the existing lifecycle boundary. Restrictive program/record foreign keys and immutable triggers were preserved; there is no new deletion door or DDL change.

Per-member notification read/archive receipts are ordinary tenant data and are now purged before their shared notice parents. Exact retained policy entries protect the two regulated-content stores against an accidentally expanded purge-table list. The schema coverage check reports these explicit policies separately and describes that retained content can block erasure. The older dropped extraction-log list entry was removed without restoring a dead store or expanding a dead-store baseline.

## Verification

- Six actual PGlite cases apply the canonical new migrations: signed QMS prose, legacy metadata-only QMS versions, and frozen input content each refuse before any purge write; a genuinely empty requested tenant can purge ordinary test content while another tenant's controlled/frozen records survive; a missing store and actual database SELECT denial both refuse. The tests were red before the preflight.
- The final five-suite run passes 58 cases, including existing audit rollback, protected Vault scope, offboarding state, and HTTP error-envelope behavior. The positive test invokes the real chained audit writer on the fixture transaction; this is not a production signing qualification.
- A separate native PostgreSQL fixture proves the concurrent insertion boundary using the actual service and two connections. An uncommitted frozen-input insertion makes the purge wait on a real database lock; after that insertion commits, the purge sees it and refuses. Both tenants' documents remain, the target stays pending deletion, and no purge-success audit row exists. The named fixture database is created only if absent and removed after all connections close. `retention-lock-proof.mjs` and its raw log preserve the reproduction.
- The fresh verification database is queried read-only by the coverage guard. It passes with no new unreachable stores. Hundreds of older stores remain outside the purge reach; this pass is no new regression, not qualification of complete tenant erasure. The existing coverage baseline was not expanded.
- Changed source lint has zero errors and one preexisting file-size warning. Independent source review found no confirmed P1/P2 in this preflight and corrected the legacy fixture to preserve its metadata-only semantics.

The native lock proof uses synthetic data in a separate local database; it does not purge a production or verification tenant, invoke an external storage provider, or establish production RLS/audit-HMAC qualification. The verification logs retain environmental audit-initialization warnings from imports; every purge query in the native negative proof uses the explicitly supplied native transaction client.
