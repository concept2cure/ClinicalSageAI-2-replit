# Durable exact-source receipt storage preparation

14 October 2026. W1/D2 read-only preparation on the current local `concept2cure-v2` tree. No application, migration, test, dependency, database, provider or deployment changes were made. The recommendation below requires the control tower's published contract before implementation. It preserves the completed source-access slice and the earlier scientific preview, recovery, storage and validator work.

## Recommended bounded increment

Add one **public, integer-organization, immutable metadata ledger** for exact extraction/actor/range **host-admission** receipts, issued through the existing offset-read host path behind a default-off server flag. Each current offset window becomes a one-range manifest; the same validator/store can support a bounded range list without adding a new tool or passage-selection implementation. Leave `vault.document_read_receipts` and its aggregate legacy coverage unchanged. Provide a separate exact-actor/extraction coverage query for evaluation/shadow use, not an automatic upgrade of the legacy catalog gate.

This increment should include the migration/applier/RLS contract, one canonical writer/reader, stable server idempotency identity, viewer-read authority, unchanged-payload binding, host integration and the full tenant export/purge/legal-hold behavior. It should **not** include provider-served status, prepared/submitted lifecycle transitions, generation/checkpoint/restart guarantees, authoring V2 save/export propagation, table context inference, new model calls or an alternate RAG store. Those belong to the broader [AnA V2 retrieval specification](../../../reports/data-room-research-2026-10-14/ana-retrieval-spec.md).

Durable exact identity is not durable reconstruction: a metadata ledger can reject a changed extraction but cannot reproduce erased earlier extraction text by its SHA alone. The first ledger should store hashes/ranges and actual host context identity, not raw source text, prompts or completions. When current text is unavailable, report historical identity and unresolved re-verification. Do not claim an exact old model context can be replayed unless a separately authorized retained payload/turn blob actually provides it.

## Proposed ledger contract

One row per source document within one server-owned host admission. A logical tool-result admission may contain one or several documents; all its rows are inserted atomically. Initial callers remain existing single-source offset reads. Proposed table name: `public.ana_source_read_receipts` (root may choose the final name).

- `id UUID PRIMARY KEY`, server assigned before first persistence attempt.
- `organization_id INTEGER NOT NULL`, `actor_id INTEGER NOT NULL`, `program_id UUID NOT NULL`, `document_id UUID NOT NULL`: exact recorded identities. Organization FK must not cascade. Source/program FKs, if present, must RESTRICT ordinary hard deletion; purge removes ledger rows through its door before parents. Actor deletion must not SET NULL or rewrite an immutable receipt; retain numeric historical actor identity without a cascade.
- `protocol_version` and `checker_revision`: fixed version strings checked against supported values; no unknown-version coercion.
- Original `content_hash`, entire `extracted_text_sha256`, actual `total_chars`: strict SHA format and positive integer text length. All source hashing is server-computed from authoritative stored text.
- `ranges JSONB NOT NULL`: bounded, validated immutable list of range ID, `[start,end)` in JS UTF-16 units, exact slice UTF-8 SHA and initial `role:body`/text-only anchor status. One to 32 ranges, safe integers, no empty/out-of-bounds ranges. Full extraction/actual slice checks repeat at insertion. A source cell/header/footnote role cannot be accepted because a model supplied the label; structural associations remain unestablished until their own extractor contract exists.
- `source_payload_sha256`: SHA of the exact whole serialized handler result admitted unchanged by the host. It is not a prompt SHA, provider request SHA or provider acknowledgement.
- `host_admission_id UUID NOT NULL` and bounded `tool_use_id`: minted/carried by the host, not parsed from model/body output. Add actual server `thread_id`, `turn_id` and `run_id` only when established; optional unknown values remain null, not fabricated IDs.
- `context_state` fixed to `host_admitted` for this increment; `created_at` database clock. Do not define unsupported served/accepted/approved columns or mutate this row into a later stronger state.
- Immutable canonical `fingerprint_sha256` over protocol, all identities, source/extraction hashes, total length, range manifest, exact payload hash and admitted host/context identity. Compare complete semantics on idempotent replay, not only this one hash.

Recommended idempotency key: `(organization_id, host_admission_id, document_id)`, with a separate receipt UUID. Repeated exact writes return the same row/ID and do not add history. Same key with different actor, source/extraction/ranges/context or payload refuses. Fresh source/actor admission happens **before** revealing an existing row on retry. A new random admission UUID on every retry is not idempotency; carry the original server key through the bounded host attempt. Process-restart replay is not promised without durable host checkpoint identity.

For several document rows in one admission, no partial accepted receipt group may survive a failing source or INSERT: use one transaction, verify all snapshots, insert/check all rows, then commit. A future multi-range row still identifies one extraction and source; do not join ranges from different documents/extractions and call them contiguous. Coverage uses range union, not sum or furthest end.

The fingerprint identifies recorded semantics and conflict/replay integrity; it is not a signature, timestamp authority or independent tamper-evident seal. Ordinary DML immutability must be tested separately. Reference an actual existing sealed turn/audit record only when one exists; do not fabricate such a link or claim resistance to privileged DDL/admin bypass from an append-only trigger test.

## Read authority and RLS compatibility

The canonical writer must freshly admit current **read** authority and stamp the fresh role on its transaction. A viewer can record a source observation they are allowed to read; this grants no catalog suggestion, correction, review or artifact write. Keep the existing governance-role checks unchanged.

At minimum, new ledger FORCE RLS must enforce numeric tenant ownership and structural source/program/actor consistency, while every interactive receipt writer/reader also enforces canonical current actor/private-project scope with explicit SQL predicates before count/LIMIT. A tenant-only policy is defense in depth, not a private-project rule. If the root requires direct database actor/project protection as well, add a restrictive policy using a transaction-local **server-admitted** actor/program scope, with strict parsing and cleared LOCAL context, rather than copying the JS sharing rules into an independent SQL policy. Do not reuse UUID `app.current_user_id` as a numeric actor ID; the existing numeric authenticated/tenant machinery is distinct.

Any actor restriction needs two deliberate non-interactive paths: authorized admin/owner full tenant export of all ledger rows, and the exact NOLOGIN purge role's controlled erasure. Test these with the actual final policies and sweep installed. An actor-filtered export with no reported failure/truncation would otherwise look complete while omitting other actors' history. Do not use a permissive extra policy as the actor constraint, nor a stale request role as read authority.

The first exact coverage function should take server actor/org/program/doc, current original/extraction identity and an explicitly named history scope. Re-admit current access and source eligibility, query exact actor + full extraction + protocol/state, validate manifests and calculate the range union. Historic legacy/null/other-actor/other-extraction rows cannot satisfy it. A malformed historical manifest is unavailable/refused, not silently ignored into an allegedly complete result. Exact actor/extraction history remains distinct from current-turn/model-request context; thread-null rows cannot be coalesced into current-thread proof.

## Lifecycle and retention decision to publish

Recommended initial classification is a **customer-owned, immutable source-observation metadata ledger**, exported with the tenant and erased only through the authorized offboarding door. Keep no raw text/prompt/completion in it. Keep no automatic TTL job in the first increment; receipt history remains through ordinary source soft deletion, withdrawal and supersession. Source eligibility is evaluated at consumption, not by deleting old receipt rows. Legal hold prevents authorized erasure, and a recorded receipt does not itself grant continued source access.

This classification is a proposed root decision, not a statement that every host-read receipt is a regulated decision or that the existing draft policy automatically requires perpetual retention. If later governed approvals/submissions reference these IDs as required evidence, their usage/retention/legal-hold dependency must be contracted before that consumer launches. Until then, authoring V1 and global filing qualification remain unchanged.

Implement one named purge door plus `PURGE_DOORS`/`PURGE_CHILD_TABLES` entry and export/purge coverage tests. Place it before source/program/actor parents. The door must require platform scope, organization pending deletion, and the existing successful untruncated same-tenant export precondition through the canonical offboarding service; return actual receipt counts for the chained purge audit. Missing required hold schema or failed hold read must refuse, not equal no holds. Reserve active-hold visibility through deletion (for example a short legal-holds SHARE reservation before a fresh check) and the organization state so a concurrent hold/status change is not invisible. No ordinary FK cascade or daily retention sweep may bypass the door. PUBLIC function execution and runtime role membership in the purger must be denied; function body/search_path/role grants must replay unchanged.

Prove the lock order across the **whole offboarding transaction**, not just the new function. The current source writer reserves catalog/documents before it holds organization/member rows. A purge that first holds the organization `FOR UPDATE` and later needs Vault DELETE locks can deadlock against that order. Prefer a pending-state `FOR SHARE` reservation, which fences status UPDATE while remaining compatible with read admission, and a fixed source/ledger/hold order verified in real independent sessions. Do not hold an access lock across external model or storage-network operations.

Existing policy/applier/offboarding gaps remain explicitly outside this increment: the retention job snapshots active holds before individual disposal, some older purge doors check holds without an insertion barrier, and the offboarding window is not a new proof that all predicate-rule record-retention conditions have been discharged. Qualify the new ledger's own door without claiming all historical erasure paths are repaired.

| S02 actor mixing | Two actors read complementary windows; null/historic legacy spans also present | New actor scope cannot union another actor/unknown protocol into full coverage. |

| S04 raw tenant and source mismatch | Foreign org/document/program/actor combinations | Real forced policies/constraints reject or expose no foreign rows. Service additionally refuses private/no-anchor/duplicate-anchor source scope. |
| S05 idempotent replay | Same host key/input twice, then one field changed | One row/one ID for exact retry; conflicting replay refuses; concurrent exact workers cannot duplicate. |
| S06 multi-range identity | Nonzero ranges, overlap, holes, repeated quote, changed slice/full SHA | Exact source slices and union coverage; no prefix reload, sum-of-endpoints completeness or `indexOf` locator guessing. |
| S07 invalid manifests | Unknown version/fields, decimals/negative/out-of-bounds offsets, >32 ranges, wrong digest, malformed JSON | Deterministic refusal before accepted insert/count; no partial group. |

These are acceptance specifications, not tests run in this read-only preparation. Use deterministic fixture hashes and independent sessions under real PostgreSQL for RLS/immutability/idempotency/race claims; PGlite/mocks are labelled sequential/unit proof. Do not add claimed time/cost/accuracy improvements before a permitted benchmark.

## Proposed implementation ownership after approval

- Schema/lifecycle owner: one additive migration, exact migration-set insertion, immutable guards/controlled door, export/purge integration and schema/runtime-role tests.
- Receipt owner: shared strict range/snapshot protocol, pure fingerprint/coverage validation, canonical store/lookup and source reservation reuse. No host or tool edits by this owner.
- Host owner: stable server admission identity/context, guarded exact payload handoff, cancellation and result disclosure in the two existing hosts/tools. No provider lifecycle state or old transcript replay upgrade.
- Independent reviewer: fail-first fixtures, forced final policies, exact source/migration hashes and genuine owned PostgreSQL concurrency/cleanup evidence.

Publish table shape, idempotency semantics, viewer authority, retention classification and default-off compatibility behavior first. Do not add several partially independent receipt writers, replace canonical source policy, or mass-implement the broader V2 design before this contract is frozen.
