## Goal

C2C runs in two AWS environments the founder controls, staging and production, each created by Terraform from this repository and each showing "No changes" on a second plan. Every production release is the exact container image that passed CI and the staging smoke test, promoted by digest, never rebuilt. A failed smoke test rolls the service back on its own. The API task holds only the runtime database role, never the RDS master credential. It is sized so a PDF/A or OCR job cannot starve it into a health-check restart. Long eCTD compiles finish behind the 60-second edge. An auditor can read the apply logs, the run URLs and the image digest for each release and trace production back to a tested commit.

## Why it matters

- There is no customer environment. `deploy-aws.yml` and `provision-database.yml` have never run (0 runs each), and the only tag is `v1.0.0`. The pilot is defined as one AWS production environment, so no customer date can be committed until Stage 5 succeeds.
- The first apply cannot even start. The Terraform state bucket name `c2c-terraform-state` belongs to someone else in eu-west-1, and it is hard-coded in bootstrap and both backends. Bootstrap fails with `BucketAlreadyExists`.
- If the web tier is compromised, the attacker holds the RDS master credential. That role owns every table, bypasses RLS and can drop the audit tables, so one leak defeats tenant isolation and Part 11 audit immutability together (OPS-16). `/api/tenants` already serves live requests through that owner connection.
- A pilot user compiling a real IND can get a 504 and lose the compile verdict, which arrives only in the response body. Their retry records a second compilation (OPS-17).
- One vCPU carries Node, clamd, LibreOffice, OCR and veraPDF with no cap on converters. One large submission package can fail the container health check, and ECS then replaces the task mid-job and drops every session on it (OPS-13).
- A GxP buyer's computer-system-validation reviewer asks two questions: is what runs in production what you tested, and how do you roll back? Today production rebuilds from source with unpinned apt packages, there is no staging, and rollback is a comment (OPS-10, OPS-23).

## Do not

- Do not run the first `terraform apply` before Stage 1 lands. Renaming buckets, switching gp2 to gp3, changing the engine major or removing the worker after creation means replacement or a storage-optimisation window.
- Do not remove the API task's owner credentials by appending a DROP or REVOKE migration, or by moving `ensureCoreTables` DDL into a new boot path. The DDL moves into `C2C_MIGRATION_FILES` as additive files, and only `scripts/db/deploy-migrate.mjs` runs it (Rule 1).
- Do not keep `cerv2-staging-deploy.yml` beside the new staging target, add a second converter limiter, a second SSE helper or a second readiness verdict. One implementation per capability.
- Do not make production deploys rebuild "just this once" to get past a missing `staging-verified-` tag, and do not set `ALLOW_NON_CANONICAL_PUSH=1` or create a release branch for the deploy. Tags go on `concept2cure-v2` commits.
- Do not add a new `*_ACCEPT_*` override (such as `RATE_LIMIT_ACCEPT_MEMORY`) to get a boot through; Stage 2 makes every such override a production boot refusal.
- Do not fence or delete CMC / Module 3 or Reporting & analytics code while trimming the image or task; both are in the launch catalog, and the boundary is the one in `shared/constants/launch-scope.ts`.
