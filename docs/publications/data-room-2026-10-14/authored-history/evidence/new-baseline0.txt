1. Executive Reassessment
This report translates the current code reality into the next cleanup and integration program. It is based on the current cleanup workstream against concept2cure-v2, including verified stage evidence through Stage 7, the live shell/workspace files, and the current compare state between the workstream and the base branch.
What is now clearly true in the code:
• The shell truth is materially better: /client-portal is fenced back into /concept2cure, root entry is quieter, and the primary beta path is more believable.
• ZenApp is the real shell and ProjectWorkspaceShell is still the strongest governed surface in the product.
• The test net is better than before: shell tripwires, auth/db contract tests, backend route smoke, governed workspace tripwires, and Stage 7 Playwright route heartbeat checks.
• The workstream also introduced new product-facing shell and UI work beyond the earlier cleanup notes, especially in ZenApp, ZenSidebar, top-nav behavior, and the pulse-test layer.
What is still true and still dangerous:
• The cleanup branch is now materially diverged from concept2cure-v2. This is now a merge problem, not just a cleanup problem.
• ZenApp.tsx remains the largest client blast-radius file. It has improved, but it still concentrates project identity, shell routing, embedded module hosting, handoff state, and chat context shaping in one place.
• App.jsx still carries too many secondary and compatibility routes. It is less dishonest than before, but it is still a route museum.
• Most of the new test coverage is still contract or tripwire coverage. The product needs more authenticated pulse checks before deeper surgery.
• Documentation discipline remains weaker than code discipline. Stage evidence often proves the work, but not always with a clean single commit chain.

5. Stage 9 — Authenticated Browser Pulse Certification
Mission
Turn the current shell and workspace cleanup from good anatomy into a real heartbeat. Extend the existing Playwright pulse pack so the team can prove the beta-safe click path works with seeded auth, project selection, governed workspace entry, and document-open flows.
Why this stage exists
• Current shell tests and workspace verifiers are useful, but many are still source-shape or route-policy tests.
• Stage 7 added real route heartbeat checks; the next move is to deepen them along the actual beta path.
• Human beta should not start before the product can prove root entry, login redirect, project route, workspace load, and governed open flows.
Files / surfaces in scope
• tests/e2e/workspace-smoke.e2e.ts
• client/src/App.jsx
• client/src/concept2cure/router/ZenRouter.tsx
• client/src/concept2cure/ZenApp.tsx
• client/src/concept2cure/components/workspace/ProjectWorkspaceShell.tsx
• Any seeded auth helpers or token utilities used by the current pulse tests
Protected in this stage
• Do not redesign the shell.
• Do not widen into full feature-depth end-to-end coverage.
• Do not use brittle test hacks that certify the wrong thing.
Multi-agent roster
Required work order steps
1. Create docs/beta-work/stage-9-authenticated-pulse-certification.md.
2. Expand the current PULSE suite to cover: root entry, login alias redirect, /client-portal/* fence, authenticated /concept2cure/project/:projectId entry, project selection from the shell, workspace shell visibility, open existing artifact, return to workspace without losing state.
3. Capture screenshots or trace artifacts for each pulse step.
4. Separate route truth, workspace truth, and document-open truth so the proof pack is understandable.
5. Document any environment assumptions used by the pulse pack, including seeded auth, token injection, local storage state, and project seeding.
6. Flag any remaining step that still relies on structural test proof rather than browser proof.
Required outputs
• docs/beta-work/stage-9-authenticated-pulse-certification.md
• Updated tests/e2e/workspace-smoke.e2e.ts or a new focused pulse file
• Screenshots / traces for root, login, fence, project-route, workspace shell, artifact-open, return-state
• Founder summary with pulse pass/fail status
Validation / proof requirements
• Root entry must never settle into /client-portal/*.
• Login redirect must preserve a usable returnTo for protected project routes.
• Authenticated project route must land in the real shell, not a placeholder screen.
• At least one document-open flow must be proven from the workspace shell.
• At least one return-to-workspace continuity check must be proven after opening a document.
Stop conditions
• Stop if the pulse pack starts certifying mocked behavior that a human beta user will not actually see.
• Stop if the test helper bypasses the very redirect or shell logic it is supposed to prove.
• Stop if the team starts calling these tests full E2E when they are still pulse checks.

• ZenApp is now clearly the real shell, but it still concentrates too many concerns.
• The branch already fixed one real ZenApp runtime failure, which proves the file is sensitive.
• Future cleanup will be safer if the file is organized by domain seams instead of endless conditional rendering.
Files / surfaces in scope

• Do not move governed workspace orchestration out of ProjectWorkspaceShell.
• Do not redesign visible UX beyond what falls out of safer seam extraction.

8. Stage 12 — AnA / Artifact / Governed Work Contract Enforcement
Mission
Make AnA the enforced system law for meaningful generation, not just the visible guide. Every valid AI generation path must either route through AnA orchestration or land in the same artifact + editor + lifecycle + audit contract. Anything else is a bypass and must be eliminated or fenced.
Why this stage exists
• The shell and workspace are cleaner, but the real moat is governed work, not just better navigation.
• AnA is already central in the shell, but the system still needs a single enforced document action contract.
• This stage protects against silent fragmentation and future regressions.
Files / surfaces in scope
• server/routes/ana-ri.ts and associated AnA service layers
• client AnA entry surfaces including AnaPersistentPanel and any remaining AI generation entry points
• artifact creation and editor handoff routes used by AI-driven flows
• tests for AI entry points and artifact creation behavior
Protected in this stage
• Do not widen into prompt-theory rewrites without enforcement value.
• Do not create parallel artifact pipelines.
• Do not bless preview-only generation flows as acceptable.
Required work order steps
1. Create docs/beta-work/stage-12-ana-artifact-contract.md.
2. Audit all AI entry points across chat, inline actions, editor actions, submission tools, templates, and exports.
3. Define the required document action contract fields, including document type, project, source, intent, content, provenance, version, and status.
4. Add enforcement or logging so generation without artifact creation is flagged or blocked.
5. Add artifact quality gates for minimum structure, no placeholder filler, and evidence-classification expectations where applicable.
6. Add tests that prove a representative set of AI entry points create governed artifacts that open in editor and initialize lifecycle state.
Required outputs
• docs/beta-work/stage-12-ana-artifact-contract.md
• AI entry-point audit table
• Artifact quality gate implementation
• Tests for no-bypass AI generation
• Founder summary with remaining bypass paths, if any
