# Filing capability audit — Concept2Cure v2 / AnA 1.0 RI

Read-only source inspection, 2026-10-14. Checkout: `concept2cure-v2`, HEAD `87b27c897c5d1be20b0527009bcaf425ebbf3af6`. No production changes, model calls, agency calls, credential inspection or test execution. This is implementation evidence, not proof of deployed operation, regulatory conformance or accepted submissions.

## Finding

The strongest foundation is a governed, deterministic evidence-to-authoring-to-filing chain. The existing global catalog, region profiles and retained MDX engines describe a much wider ambition than the current launch workflow and qualified agency delivery support. Improvements should strengthen that chain and qualify bounded adapters, while keeping catalog visibility, authoring support, packaging, validation and agency acceptance as separate claims.

## Concrete hardening opportunities found by source reading

1. **Align eSTAR assembly, filing currency and AnA wording.** `assembleDeviceSubmission` sets `canProduceOfficialEstar` from completed sections and template presence, excluding `template.versionCurrent`; the AnA handler then instructs not to claim submittable unless this boolean is true. The dedicated filing-readiness engine does include currency. A filled old official artifact can be physically producible while it is not a current fileable submission. Use one canonical contract that names these distinct states and reuse it across tool, page and export. [Assembly formula](/workspace/Concept2Cure/server/services/pathway-engines/device-assembly/assemble-device-submission.ts:209), [AnA instruction](/workspace/Concept2Cure/server/services/ana/AnaToolExecutor.ts:16801), [filing formula](/workspace/Concept2Cure/server/services/pathway-engines/estar/estar-filing-readiness.ts:331). Static discrepancy; no reproduced test claim.
2. **Make outdated currency evidence consequential.** Dedicated eSTAR filing readiness calculates `versionTableStale` yet omits it from `canFileNow`. A present version table is not fresh evidence forever. Establish what stale verification means in the existing dated currency policy and test the chosen consequence. [Current computation](/workspace/Concept2Cure/server/services/pathway-engines/estar/estar-filing-readiness.ts:275). Static finding; no claim that current 2026-10-05 record is stale today.
3. **Reconcile market promise with retained EU technical-file capability.** Market offers say no device package, but a governed backend route can export real Annex II/III files. Decide its usable workflow and status, then have the existing offer/gate reflect exactly that bounded outcome; do not build a second packaging service. Preserve author-only status where no qualified finish exists.
4. **Correct stale source assertions during implementation.** Leaf resolver header still describes Vault leaves as unresolved; `ind/ctd/submission-chain.ts` and `fda-technical-rules.ts` still describe XML intake refusal. Actual branches/format registry supersede those claims. Avoid feeding AnA these old limits as present facts. [Stale chain statement](/workspace/Concept2Cure/server/services/ind/ctd/submission-chain.ts:109).

## Adapters that could create reusable client value

| Priority / adapter | Bounded starting point | Client and moat value | Gate before widening |
| --- | --- | --- | --- |
| First: evidence-change propagation | Add typed dependencies to existing source version → locator → claim/number → authored section → exported artifact. A new source or changed data cut invalidates affected outputs and creates review work. | Pharma summaries, device design/risk claims and diagnostic performance values can share one provenance substrate. Customer-specific accepted evidence mappings and reviewed resolutions accumulate reusable value. | Deterministic invalidation; reviewer authority; no silent regeneration/reapproval; exact source/version/hash and field/table locator. |
| First: IVD evidence contract | CSV/XLSX retained bytes → named specimen/analyte, matrix, assay lot, instrument/software version, units, reference standard, pre-specified cutoff/population → deterministic qualified calculation → PER/eSTAR attachment. | Next: device evidence contract | Connect intended use, design inputs, risk controls, verification/validation results and software configuration to governed claims/attachments. | Reusable device evidence across 510(k), De Novo, PMA, MDR and product change assessments; supports diagnostics software and companion diagnostics. | Actual typed mapping and applicability, not title matches; distinguish design change/evidence impact from automatic regulatory classification. |
| Next: pharma locked-study adapter | Exact dataset bytes/version/hash plus study ID, database lock, SAP, populations and calculation manifest into one supported CSR table. | Removes the current body-supplied result seam and gives numerics portable traceability into CSR → M2.7 → M2.5. | Native XPT/SAS/Dataset-JSON and study-data packaging require product-scope decision already deferred; begin only with authorized formats and a stated calculation contract. | Next: jurisdiction package/receipt contract | Qualify FDA package plus one real transport first, retaining standards/rule versions, validator output bound to ZIP hash and full genuine ack chain. Applicant portal handoff is valid where API is unavailable. |
| Later: protocol-specific adapters | US IVD eSTAR then EU IVDR/NB bundle; pharma EU CTIS Part I/II and IMPD; JP marketing v4; Canada CTA/marketing; chosen ACTD/CTD countries by customer demand. | Broadening happens with evidence, preserving common evidence reuse while respecting different forms, units/language, authorities and Member State content. | Bound by application + product class + jurisdiction + lifecycle + effective rule revision, with explicit supported/not-assessed/unsupported states. |

These are proposed product directions, not novelty claims: the code audit cannot establish that competitors have not deployed them. The defensible combination is inspectable source-to-result-to-claim-to-filing reuse, retained customer reviews, licensed/datable rules, bounded scientific calculations and a proven agency delivery loop.

## Existing founder-deferred scope

The 2026-10-08 data-room decision explicitly defers `.xpt`, `.sas7bdat`, Dataset-JSON, `m5/datasets` packaging and dataset ZIP intake. Section 6 states: “The following need the launch catalog extended (D2) and change what row D7 proves, so no session may start them without a founder decision.” [Exact source](/workspace/Concept2Cure/docs/design/DATA_ROOM_CATALOG_AND_CLINICAL_DATA_2026-10-08.md:109). This research does not start them or ask for permission now. Keep them named as the future bounded dataset increment, separate from improvements to currently authorized CSV/XLSX profiling, metadata governance and evidence lineage.

Repository Rule 2 also keeps causal/self-evolving/federated/digital-twin engines out of launch until D1–D10 are green; no reason to equate a traceability implementation with those deferred module names.
