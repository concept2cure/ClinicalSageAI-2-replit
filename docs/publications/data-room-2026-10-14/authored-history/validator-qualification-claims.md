# D7 validator qualification and claim review

Read-only review, 14 October 2026, HEAD `87b27c897c5d1be20b0527009bcaf425ebbf3af6`. No app edits, validator executions, credentials or transmissions. The filing-adapter plan was also reviewed: no material regulatory interpretation error found.

**Finding:** the runtime seam and several documents use “agency-grade,” “external,” “configured” and “accepted” too broadly. A vendor pass is a scoped technical result; it is never itself agency acceptance. The internal FDA subset cannot satisfy a requirement for independently qualified validation merely because it implements the same interface.

## Precise status language

| Proven state | Permitted wording | Evidence needed for the next claim |
| --- | --- | --- |
| Internal subset ran | “Internal pre-check completed: no blocking findings in the implemented FDA subset.” | Independent engine execution and declared coverage; retain subset limitations. |
| Adapter configured | “Validator adapter endpoint/path configured; execution and qualification unverified.” | Actual tool identity/version, usable licence where required, reachability, correct profile and qualification. Current `isConfigured()` proves URL presence or filesystem accessibility only. |
| Tool completed | “Named tool completed for this package; report retained.” | Report authenticity, completion state, input-package binding, tool/profile/criteria versions, declared coverage and unresolved findings. |
| Scoped independent validation passed | “Package SHA-256 … passed independent technical validation with engine … version …, profile …, criteria …; coverage …; limitations ….” | Sponsor review/release and actual authorised submission. Scope does not extend to scientific sufficiency, another region/version or another package. |
| Agency receipt/technical acknowledgement received | “Authority received the identified submission” or the exact documented technical disposition. | The relevant centre/authority's subsequent acceptance/review disposition, matched to the submission. Transport receipt does not prove technical or scientific acceptance. |
| Actual authority decision | “Authority accepted this submission for [specified stage], evidenced by [dated reference].” | Marketing/conformity authorisation is a separate decision unless the recorded decision explicitly establishes it. A test-system receipt is labelled test evidence. |

## Primary-source boundary

FDA's current table names **LORENZ eValidator 25.2** for CDER/CBER eCTD, in use from **25 August 2026**, and validation criteria **v4.6** supported from **28 August 2026**. It separately lists Pinnacle 21 for study-data standards. This substantiates a scoped tool/version reference; it does not establish that all agencies or submission types use only one tool, that sponsors must buy that vendor, or that a matching vendor pass is an authority decision. [FDA v3.2.2 submission standards/tool table](https://www.fda.gov/drugs/electronic-regulatory-submission-and-review/ectd-submission-standards-ectd-v322-and-regional-m1).

FDA also distinguishes ESG account testing from optional sample submissions and final production submission. Preserve those distinctions in D7 acceptance evidence. [FDA Submit Using eCTD](https://www.fda.gov/drugs/electronic-regulatory-submission-and-review/submit-using-ectd). MHRA states it uses LORENZ docuBridge for technical eCTD validation—a different named product/route statement, not evidence of a universal LORENZ eValidator requirement. [MHRA medicine licensing guidance](https://www.gov.uk/guidance/apply-for-a-licence-to-market-a-medicine-in-the-uk).
